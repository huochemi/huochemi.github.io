# 拍摄与整理工作流（photo-workflow）

本文件记录**人的使用习惯**与**由此推出的产品定位/定义**。程序侧的坑分别见
`toolchain.md`（构建/框架）、`data-pipeline.md`（管线机制）与
`photo-metadata.md`（EXIF 元数据口径）；本文件回答的是"这些照片是怎么来的、
为什么要这样组织、因此哪些行为算正常、哪些算未完成"。

## 产品定位（用户 2026-10-05 系统阐述）

**一句话**：本站是**火车迷的地图**——标出"哪些地方适合拍车"，并回答每个点位的四件事：
**在哪、怎么去、周围什么样、我在那儿拍到了什么**。

**目标用户**：火车迷 / 铁道迷（railfan）——会专程外出"拍车"的人。

**产品定义（用户 2026-10-03 明确；2026-10-04 扩展到视频）**：本站的功能就是
**在地图上展示照片与视频**，因此坐标不是可选元数据，而是媒体能否进入产品的
必要条件——**没有坐标的媒体无法展示**，所有照片与视频都必须有坐标。
视频（mp4）的管线机制见 `data-pipeline.md` 视频小节、元数据口径见
`photo-metadata.md` 视频小节。

### 内容模型：点位 × 内容

产品的原子单位是**点位**（= 一个 `photos/<地点>/` 目录 = 地图上一个 marker），
**不是单张照片**。每个点位回答访客四个问题，恰好对应三类内容：

| 访客的问题 | 内容 | 来源设备 |
|---|---|---|
| 在哪？怎么去？ | 坐标（可导航） | 手机照 GPS（或 `fix-gps` 复制的锚点坐标） |
| 周围什么样？ | 环境照（广角） | 手机 |
| 在这儿能拍到什么？ | 主体作品（长焦）+ 视频 | 相机 / 手机 |

三类内容的关系决定了"典型 dir"的形状（先手机照定位 + 环境，再大量相机照），见下节。

### 增长模型：内容驱动，不是时间驱动（关键）

产品增长**不是**"去一次拍一次、照片越积越多"的线性模型，而是**点位驱动 + 内容驱动**：

1. **点位数量有限且趋于收敛**——一个城市适合拍车的机位就那么几个，不会短时间内暴增。
   用户原话："一个城市的定位点可能就只有那几个，不会短时间内增加很多。"
2. **单个点位会饱和**——点位一旦已记录"周围环境 + 火车照"，**继续堆同质照片对产品没有
   意义**（同一机位、同一车型，加第十张不产生新信息）。用户原话："单纯的增加该定位点
   的照片对于当前产品来说并没有什么意义。"
3. **新增的触发条件是"新内容"**——新型号 / 新涂装 / 特殊编组 / 季节性画面 / 罕见车。
   用户原话："除非我在该定位点拍了一个新的型号的火车，那么我会增加到该定位点。"
4. 因此**大量拍摄素材不会进入产品**——只有构成"新内容"的精选才入库。稳态增长远低于
   "每次外拍的照片数"。

**外部佐证**（2026-10-05 调研，非推测）：火车迷拍车文化本身即**围绕"机位"组织**——
北美有 Spotatrain 这类以地点为目录的机位库（Tehachapi Loop、Cajon Pass 等经典机位），
国内亦有"落坡岭""十渡蝙蝠山"等公认圣地（《李睿的铁道摄影手记》）。拍车讲求**时空
稀缺性**：同一机位，往往要等到特定车次 / 季节 / 光线才值得按下快门。这与"点位有限、
新增靠新内容"的模型一致。

**对容量评估的意义**：此前用"09-13～10-04 的 29 MB/天"外推撞线时间，那是**早期集中
导入期**的最坏值，不是稳态；按本定位，稳态增长由"新增有效点位 + 新增有效内容"决定，
远低于线性外推。**但这不改变存量问题**——已有 153 个 / 598.8 MB 原图是既成事实，容量方案仍须
处理它。容量评估详见 `docs/plans/2026-10-04-data-repo-longevity.md`。

### 产品边界（明确"不做"）

- **不是照片归档站**：只展示构成"新内容"的媒体，不是拍摄素材的全量备份库
- **不是社交站**：无用户体系、评论、点赞
- **不含无坐标媒体**：坐标是进入产品的必要条件（硬拦，见「由此推出的设计约束」）

## 拍摄习惯

外出拍火车时同时带**手机**与**相机**，两台设备分工固定：

| 设备 | 角色 | 产出特征 |
|---|---|---|
| 手机（如 iPhone 14 Pro Max） | **坐标锚点 + 环境说明** | 广角，EXIF 自带 GPS；每到一处先拍几张 |
| 相机（如 SONY NEX-5N） | **主体作品** | 长焦；机身**无 GPS 模块**，同一地点会连拍大量 |

一个典型 dir 因此长这样：**先几张手机照（定位 + 环境），再大量相机照（主体）**——
对应「产品定位」里三类内容的前两类：手机照回答"在哪、怎么去、周围什么样"，
相机照回答"在这儿能拍到什么"。

## 标准数据流程

1. 从设备导入原始照片（与视频）到 **`../photos-originals/photos/<地点>/`**（原图仓）。
   **2026-10-05 形态 B 起原图不再进 data 仓**（见 `data-pipeline.md`「双根管线」）；
   **新建点位要在两侧各建一次目录**：原图仓放原图、data 仓
   `../data/photos/<地点>/` 放 `index.json` 与派生图（步骤 3/4）。
   视频注意：iPhone 拍的 mp4 自带 GPS / 拍摄时间 / 设备，**不需要 fix-gps**；
   原片只留在原图仓，入库的是 `npm run photos` 产出的转码版 `<名>_web.mp4`（落 data 仓）
2. `npm run fix-gps -- <地点>`：把手机照的坐标复制到相机照
   （同目录内按拍摄时间就近推荐参照；详见 `photo-metadata.md`）。
   缺坐标的**视频**与照片同清单、同写入命令（交互/批量/审阅页全部适用）。
   整个文件夹是同一地点时可走批量模式一步到位：
   `npm run fix-gps -- <地点> --ref <参照文件名> --all`（非交互，把参照坐标
   写入该文件夹全部缺 GPS 的照片；`npm run photos` 预检提示在"恰有 1 张
   带坐标照片"时会直接给出这条含参照文件名的命令）。命令可安全重跑：
   已写入的照片不会进目标列表，工具永不覆盖已有坐标。
   计划文档：`docs/plans/2026-10-03-fix-gps-batch-mode.md`
   **锚点落在多处**（≥2 张带坐标且坐标不重合）时逐张指定参照不现实——走分组审阅页
   （2026-10-03 新增）：`npm run fix-gps -- <地点> --review` 生成只读页面并打开
   （真实时间比例密度条 + 等距胶片条按拍摄时间铺开、GPS 三态标识、点图与位置代表
   并排对照）；页面调好分组后点「复制写入命令」（按钮把 JSON 压缩为单行内嵌进
   `echo '<json>' | npm run fix-gps -- <地点> --plan-stdin`，单引号按 shell 规则
   转义——JSON 与命令合并成**一次**剪贴板写入，避免"复制 JSON 后又复制命令把它
   覆盖"的单槽竞态），回终端直接粘贴回车、一次确认写入全部。
   **同位置锚点自动合并**（2026-10-04 新增）：相距 < 5 米的锚点视为"同一处"并为
   一组（`ANCHOR_MERGE_METERS`，判据与 `process-photos.js` 的同名常量必须一致），
   组代表取组内最早拍摄的那张——同地点连拍多张手机照不再各自成组，页面统计不再
   出现 0 张空组，plan 的 `ref` 用代表（组内坐标相差 ≤ 5 m，属 GPS 噪声级）。
   `npm run photos` 预检提示按锚点数量分档给命令：1 张 → `--all`；≥2 张 →
   `--review`，并附摘要（如"5 张锚点落在 2 处、最远相距 114 m"，判据同 5 米）。
   计划文档：`docs/plans/2026-10-03-fix-gps-review-page.md`、
   `docs/plans/2026-10-04-fix-gps-cleanup-and-anchor-merge.md`
3. 维护 `index.json`（**两个字段均必填**：`index_photo` 指定封面、`description`
   展示名，可为空串 `""`）。新建点位可用脚手架一次建好 data 侧目录与 `index.json`：
   `npm run new-place -- "<点位名>" --cover "<封面文件名>"`
   （`description` 取点位名写入；要换成更短的展示名，建好后直接编辑 `index.json` 再重跑
   `photos`。封面必须在原图仓中存在——脚本只校验存在性、**不校验 GPS**，
   判定权唯独属于 `npm run photos` 的预检。已有 `index.json` 时硬拦不覆盖。详见
   `plans/2026-10-05-new-place-scaffold.md`）

   **可选第三个字段 `references`（2026-10-05 新增）**：给点位挂外部参考链接，显示在
   照片详情面板的「延伸阅读」区块。它是**纯展示字段**——预检不校验它，缺省即"该点位
   没有外部链接"，故既有 `index.json` 无需回填：

   ```json
   {
     "index_photo": "IMG_4657.HEIC",
     "description": "北京市-大兴机场",
     "references": [
       { "kind": "data",    "label": "X-Plane 场景包（Scenery Gateway）", "url": "https://gateway.x-plane.com/airports/ZBAD/show" },
       { "kind": "chart",   "label": "大兴机场航图（CAAC）",              "url": "https://yinlei.org/x-plane10/web/doc/ZBAD.pdf" },
       { "kind": "article", "label": "大兴机场航图笔记（2019）",          "url": "https://yinlei.org/x-plane10/2019/09/zbad.html" }
     ]
   }
   ```

   `kind` 取 `data`/`chart`/`article`（只决定标签文字，其它值原样显示）。**只放链接、
   不搬运正文**——外部内容一律让读者点开原站看。改完同样要重跑 `npm run photos`，
   由管线透传进 `output.json`（`output.json` 是构建期打包进 bundle 的，不是运行时读取
   外部文件）。见 `plans/2026-10-05-point-references.md`
4. `npm run photos`：生成派生图 + `src/Application/output.json`
5. 三个仓库（原图仓 `photos-originals` / data / 本站点）分别提交

## 由此推出的设计约束

1. **「照片缺 GPS」是未完成的中间态，不是终态。** 相机照天生没有坐标，第 2 步补完
   才有。因此管线生成数据时，**任何一张缺坐标都意味着流程没走完**——应当尽早报错，
   而不是静默降级。用户 2026-10-03 明确："不习惯 fallback，尽量及时发现问题，
   早报错早知道。"
2. **手机照 = 坐标锚点。** 判据可复用数据层既有的 `device` 字段
   （`device === 'phone'`，见 `photo-metadata.md` 的 device 小节），无需新增字段。
3. **同一 dir 内多张照片共享同一坐标是事实，不是错误。** 补完坐标后，相机照与锚点照
   的坐标完全相同；照片分组模式下这些 marker 会**像素级重合**，属于正常数据，
   需要聚合展示，而不是当作异常处理。
4. **封面可以是手机照、相机照，也可以是视频（2026-10-04）；判据是"这张媒体能否
   代表拍摄地"。** 封面同时承担两件事：代表本组（内容/审美选择）+ 提供组级坐标
   （数据约束），因此**封面必须有坐标**。选手机照只是"顺手同时满足两个要求"，
   不是硬性规定。注意：2026-10-03 起失败判据是"**组内任一张**缺坐标即整组不产出"，
   封面不再是单独的一条硬拦。
5. **原生坐标与复制坐标应当可区分（已实现）。** `fix-gps.js` 复制坐标时同时写
   `GPSProcessingMethod` 溯源标记（`hcm-geosource ref=<参照> date=<日期>`），管线读成
   `output.json` 的 `geoSource` 字段（**无该字段 = 原生坐标**），于是能回答"这张照片
   的坐标是哪张锚点给的、锚点选错没有"。顺带修掉了原先 `-tagsfromfile` 把参照的
   `GPSHPositioningError` 一并复制所导致的"相机照声称拥有手机级定位精度"问题。
   字段选型与读取方式见 `photo-metadata.md` 的坐标溯源小节。

## 已定口径与未解问题（2026-10-03）

**已定（用户确认）**：

- 缺坐标一律硬拦，**不做** `index.json` 豁免清单（产品要求所有照片都有坐标）
- 失败粒度取 **1b**：某个 dir 缺坐标 → 该 dir 跳过、不产出任何数据；其余 dir 照常
  产出；退出码非 0
- 呈现层的静默回退（`MapChildren.jsx` 的 `photo.lat ?? group.lat`）**删除**
- `fix-gps` 增加坐标溯源标记（能区分"原生坐标"与"复制坐标"）
- 实现计划：`docs/plans/2026-10-03-gps-gate-hardening.md`（**已实现**）

**实现落点**（程序细节见 `photo-metadata.md`）：判定与预检在 `process-photos.js`
（预检零写操作，失败 dir 一张派生图都不留；全失败时不覆盖 `output.json`）、溯源写入
在 `fix-gps.js`、前端回退删除在 `MapChildren.jsx`。

**未解**：

- 照片分组模式下同坐标 marker 重合（约束 3）尚无聚合方案——模式保留，聚合另出 plan
- `geoSource` 目前只进数据层，`ⓘ` 面板尚未展示"坐标来自哪张锚点"（本轮不做）
