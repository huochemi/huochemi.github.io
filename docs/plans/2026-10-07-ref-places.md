## 背景（自包含，零上下文可读）

站点是火车迷的**照片地图**：原子单位是"点位"，地图上一个 marker 对应一个点位，
点击 marker → 抽屉显示该点位的照片网格 → 点某张进 Lightbox → `ⓘ` 面板看坐标等详情。

**关键事实（代码实读，非推断）**：marker 的唯一数据来源是
`src/Application/output.json`，而它完全由 `process-photos.js` 从这样的点位产出——
data 仓有点位目录 + **原图仓有媒体文件** + `index.json` 齐备 + 封面有坐标。
"有媒体文件"是预检链上的硬判定（`preflightDir`，
`process-photos.js:931`：`mediaFiles.length === 0` 即跳过该点位）。

**缺的能力**：还没去过的点位无法预先登记到地图上——"没去过"= 没有自己拍的照片 =
过不了那条硬判定。

**用户的真实用途**（两段，同样重要）：

1. **出发前**：把想去的点位标在地图上，附上从公开渠道找的**环境照**，先熟悉"到了那儿
   长什么样、周边有什么"，到现场能快速认出位置。
2. **到现场**：打开站点 → 大致定位到该城市 → 从地图上找到这个点位 → 点开 → **唤起高德
   导航**（打车/骑行过去）→ 开始拍车。

## 产品设计（用户 2026-10-07 阐述，已于 `photo-workflow.md` 沉淀）

三条要点，本方案全部据此设计：

1. **点位先于照片存在，但"在地图上能点"必须靠照片** —— 本站的交互入口是"点一张照片
   看详情"，所以**没有照片的点位在当前产品里没有实际意义**。参考照就是它的"入口图"。
2. **参考照承担的是「周围什么样？」这一问**（`photo-workflow.md` 三类内容中的第二类），
   与实拍点位的环境照角色完全一致 —— 所以它应当**与实拍照片数据同构**，从而复用
   现有的图钉/抽屉/网格/Lightbox/信息面板**全部代码**。
3. **参考点位不是"另一种东西"，而是同一个点位的早期阶段**：坐标 + 环境照在出发前即可
   从公开资料获得，主体作品只能到现场拍。去一次即补齐。

## 决策记录：长期结构三候选 → 拍板丙（2026-10-07）

### 根因：为什么"去过之后"本来会有"要删要搬"这件事

同一种信息（点位级元数据：名字 / 坐标 / 说明 / 来源链接）本来会住在**两个地方**：

| 阶段 | 元数据住哪 | 承载字段 |
|---|---|---|
| 未去过 | 站点仓 `refs.js`（甲方案的手写表） | `name` / `lng,lat` / `note` / `sources` |
| 已去过 | data 仓 `photos/<点位>/index.json` | 目录名 / 封面 EXIF / `description` / `references` |

而 `index.json` 的 `description` 与 `references` **本来就是为点位级元数据准备的**
（`buildGroup` 无条件透传二者，`process-photos.js:1162/1169`；`北京市-大兴机场` 正在用
`references` 挂航图与文章链接）。所以"去过"在数据层等于**元数据从一个地方搬到另一个地方**——
有搬家就有遗漏、就有删除、就有"忘了"。

### 三候选（保留以便将来理解"为什么没选甲/乙"）

| | 长期形态 | 去过之后要做什么 | 优点 | 代价 |
|---|---|---|---|---|
| **甲**<br>refs.js = 待办清单 | 站点仓 `refs.js` **永远只含没去过的**；点位元数据的最终归属是 data 仓 `index.json` | **搬 2 个字段 + 删 2 处**：`note`→`description`、`sources`→`references`（手工搬运）；删 `refs.js` 那条；删 `public/refs/<id>/` | 改动最小、当天可用；不动管线 | 每次去过都手工搬运；**忘搬即永久丢信息**（原件已被删）；条目退场靠 `output.json.dirName === refs.js.name` **字符串完全相等**，写歪一个字符即静默重影；同一种资料长期两处存放 |
| **乙**<br>refs.js = 永久台账 | refs.js 含全部点位，`status: 'wanted'\|'visited'`；地图靠同名去重隐藏已去过的 | 不删不搬，只加 `status` | 零搬运、零删除；"为什么想去"永久留痕 | **同一点位永久两处记录（违反 P3 单一事实源）**；参考图（他人作品）永久在线；表无限增长；改说明要改两处；隐藏仍依赖脆弱的同名匹配 |
| **丙（用户拍板）**<br>点位下沉 data 仓 | **一个点位 = data 仓的一个目录**；"想去"→"去过"是**同一目录的两个阶段**，不换归属地。`refs.js` 这个文件不存在 | **零搬运、零删除**；只需把参考态标记切成实拍态（同一文件内改 2 个键，见「升级路径」） | **P3 单一事实源**（点位只有一处）；"点位先于照片存在"真正落地；**地图重影在结构上不可能发生**（只有一个来源，没有去重这回事） | 改主管线三处 + 放宽一条现有硬拦（见「管线改动」）；`data/photos/` 里出现"还没有实拍照片的点位目录" |

**为什么否决甲**：判据是"债务会不会反复还"。用户当前节奏是一个城市一个点位逐步添加 ⇒
甲会让"搬 2 个字段 + 删 2 处"这个动作每去一个点位重复一次，且每次都有一个静默失败点
（搬运遗漏、同名不匹配）等着。
**为什么否决乙**：它把"同一种资料两处存放"永久化，正是用户想避免的。

**术语纠正（重要）**：丙里的新目录**不是"没有照片的目录"**——它含 `index.json`
（名字 / 说明 / 来源链接）与 `refs/`（坐标 `point.json` + 一组**参考环境照**）。它缺的只是
"**我自己拍的**照片"。产物上它与其他点位一样有图可点，故完全满足用户"没有照片的点位
没有实际意义"这条判据。

## 实现方案（丙）

### D1 判定点唯一：由"原图仓该目录有没有媒体文件"决定点位处于哪个阶段

管线**本来就在读**这个信息（`preflightDir` 第 909–923 行读原图仓目录并过滤媒体），
所以不需要在 `index.json` 里手写一个"我是参考点位"的声明字段——**判定点单一**，
不会出现"声明与实际不符"的矛盾态。

| 原图仓该点位目录 | 阶段 | 组级坐标来源 | 输出给前端的标记 |
|---|---|---|---|
| **无媒体文件** | 参考态 | `refs/point.json` 的 `lng`/`lat`（缺则报错退出） | `pinKind: 'ref'` |
| **有媒体文件** | 实拍态（现状不变） | 封面文件的 EXIF（现状不变） | `pinKind: 'photo'` |

前端只**读**这个标记（自己做视觉与文案分支），不参与判定。

### D2 坐标**不进 `index.json`**，而住 `refs/point.json`（2026-10-07 用户拍板）

**为什么改**：把坐标写进 `index.json` 的 `lng`/`lat`，就必须附一条"实拍态禁止出现它们"的
校验，于是"去过之后要记得回来删这两个键"就成了一个**靠人记住的动作**——它是本方案里唯一
的这类动作，也是设计缺陷而非必要代价。把坐标挪进 `refs/` 之后这条整条消失：

- `index.json` 的字段契约**两个阶段完全一样**，不需要任何"这个阶段不许有某键"的校验；
- 去过之后的收尾就是 `rm -rf refs/` 一条命令，**参考图与坐标一起消失**；
- 就算忘了收尾也**无害**：实拍态管线**根本不读 `refs/`**（判定点为"原图仓有没有媒体"，
  见 D1），不会出现"两套坐标谁赢"的问题。

**`index.json` 契约（唯一差别是 `index_photo`）**：

| 键 | 参考态 | 实拍态 | 说明 |
|---|---|---|---|
| `description` | **必填** | **必填** | 现状契约不变（key 恒存在、空串合法） |
| `index_photo` | **不许出现** | **必填** | 参考态没有原媒体可指；出现即报错（见下） |
| `references` | 可选 | 可选 | 现状契约不变 |

**参考态的全部痕迹落在同一个目录里**（`refs/` 即"参考态开关"）：

```
../data/photos/衡阳市-湘江公铁大桥道口/
    index.json     { "description": "…", "references": [ … ] }   ← 与实拍态同形
    refs/
        point.json { "lng": 112.6, "lat": 26.8 }                 ← 坐标（GCJ02，见 D5）
        01.jpg                                                   ← 参考环境照（01 = marker 用）
        02.jpg
```

**`refs/point.json` 契约（极简，只放坐标）**：

```json
{
  "lng": 112.6,
  "lat": 26.8
}
```

- 坐标系 **GCJ02**（D5）。⚠️ JSON 写不了注释 ⇒ 这条口径只能靠文档
  （`docs/photo-ops.md`）与 `new-place --wish` 的输出交代 —— 这是"坐标放进 json"相对
  "放进 `index.json`"唯一多出来的成本，如实记录（`index.json` 本身也没有注释，
  本库的通行做法就是靠文档约束，故不算破例）。
- `lng`/`lat` 必须是**数字**，否则报错退出（不猜、不做字符串转换）。

**参考态里出现 `index_photo` 是显式失败而非忽略**：它此时指着一个不存在的文件，
留下它就是脏字段（与 `docs/photo-metadata.md`"宁缺毋假"同口径）⇒ 报错并提示删。
反向（实拍态还留着 `refs/`）**不报错**——那是"上一阶段的遗留文件"而不是"一个说谎的字段"，
且报错会把一个完全合法的实拍态卡住；改为在管线输出里加一行 ℹ️ 提示可清理（只报告、
不改退出码，与既有"增量汇总/设备汇总"同级）。

⚠️ **现状事实（易误解，特此写明）**：`index.json` 的键**只有** `index_photo` + `description`
（外加可选的 `references`）。2026-10-07 实测全部 18 个点位：

| 点位 | `index.json` 的键 |
|---|---|
| 石家庄站 / 郑州 / 南京中和桥道口 …（17 个） | `index_photo`, `description` |
| 北京市-大兴机场 | `index_photo`, `description`, `references` |

坐标**从来不写在 `index.json` 里**，实拍点位的坐标从封面照片的 EXIF 读出（`buildGroup`）。
参考态没有照片 ⇒ 没有 EXIF ⇒ 必须由人给一个坐标，住进 `refs/point.json`。
本方案让 `index.json` 的契约**继续只有这三个键**（不新增任何键）。

### D3 前端数据形态与实拍点位**同构**（本方案的技术红利）

参考点位经管线输出后，在 `output.json` 里与实拍点位**字段同名同形**：
`lat`/`lng`/`dirName`/`description`/`references`/`thumbnailLink`/`displayLink`/`fileName`
/`photos[]`，另加 `pinKind`。于是 `MapChildren.jsx` 的 marker 渲染、`flattenPhotos`、
抽屉网格、Lightbox、`LightboxInfoPanel`、两种 `hcm_group_by` 分组模式**全部直接复用**，
无需新组件，也**没有"同名去重"**（单一来源，不存在重影问题）。

### D4 坐标是**点位级、人工标注**的单一值

实拍点位是"每张照片各自有 EXIF 坐标"；参考点位只有**一个坐标**（`refs/point.json`），
属于点位。因此：

- 参考图**共享**同一个坐标（抽屉里所有参考图落点相同；照片分组模式下会重合，属正常）。
- `ⓘ` 面板的坐标区块文案改为「**点位坐标（人工标注，GCJ02）**」，
  **不伪装成"这张照片自带的定位"**（宁缺毋假）。

### D5 坐标口径：**GCJ02**（与 `cities.js` 同一工具、同一口径）

先厘清为什么这里需要显式定口径——坐标口径在本库早就是高危区，但此前靠**结构**隔离，
不靠字段：每个数据文件只有**一个坐标来源 + 一种用途**。

| 数据 | 来源（唯一） | 坐标系 | 用途与处理 |
|---|---|---|---|
| `cities.js` | 高德坐标拾取器 | **GCJ02**（海外例外见下） | 城市胶囊落点，**直给高德，不做转换** |
| `output.json` 的照片坐标 | 相机/手机 EXIF | **WGS84** | marker 落点，**无条件** `convertFrom(...,'gps')` |
| **本方案的 `refs/point.json`** | 高德坐标拾取器 | **GCJ02** | 参考态组级坐标，**直接使用、不转换** |

规则收敛成一句话：**人手填的坐标一律 GCJ02（拾取器直接粘贴）；照片 EXIF 坐标一律
WGS84 并换算**。好处：① 与同目录的 `cities.js` **同款纪律**（照抄邻居不会错）；
② 你的实际动作是"用高德找这个道口、再从那儿导航"，拾取器本来就给 GCJ02，
零换算、零换算错误；③ 不需要新增 `coordSys` 字段，也不需要"两套口径分支"。
海外沿用 `cities.js` 既有例外：GCJ02 偏置仅在境内生效，**境外直接填 WGS84 坐标即可**。

### D6 参考图放 **data 仓** `photos/<点位>/refs/`（2026-10-07 用户拍板）

上一轮判"只能放站点仓"是把 `.gitignore` 当成了不可动的硬约束。本轮用户追问
"为什么当初要过滤 jpg、是否有必要"，复核后**改判**——判据如下表（含上一轮漏掉的口径）：

| 判据 | data 仓 `photos/<点位>/refs/` | 站点仓 `public/refs/<点位>/` |
|---|---|---|
| 点位自包含（丙的前提） | ✅ 元数据 + 素材同在一个目录 | ❌ 一个点位被拆到两个仓 |
| URL 形态 | ✅ `/data/photos/<点位>/refs/01.jpg`，与照片**同一套拼接规则**（`BASE_URL/<dirName>/<fileName>`），`photos[]` 里 `fileName` 写成 `refs/01.jpg` 即可 | ❌ 需要第二套路径规则 + 前端分支 |
| 加一个参考态点位要推几个仓 | ✅ **1 个**（data 仓：`index.json` + `refs/`） | ❌ **2 个**（data 仓放 `index.json`、站点仓放图） |
| 体积台账 | ✅ 计入 data 仓既有 1 GB 台账（现 47.9 M） | ❌ 落进站点仓的 `gh-pages` 分支，不进任何台账 |
| 需要动 `.gitignore` | ⚠️ 需要（见 D6b，已实测可行） | ❌ 不需要 |

⇒ **data 仓全面占优，唯一代价是给 `.gitignore` 开一条作用域最小的口子**（D6b）。

### D6b `.gitignore` 排除 jpg 的规则：为什么有、还必要吗、怎么开

**它的来历**（`docs/plans/2026-10-04-data-repo-longevity.md` 迁移步骤第 12 步）：形态 B 把
152 个原图 `git rm` 出本仓之后，加一条**扩展名排除**当闸门，防止原图被重新 `git add` 回来。
动机是那次迁移的核心判据：

> 派生图**可再生**（丢了重跑 `npm run photos` 就有）⇒ 只需托管、不需备份；
> 原图（母片）**不可再生** ⇒ 要异地副本，放私有仓 `../photos-originals`。
> 把不可再生的大文件（占 92.3%）留在被托管的仓里，很快撞 1 GB 配额。

**所以这条规则的真实目的是"把不可再生的大文件挡在门外"，扩展名只是它挑的廉价代理**——
不逐文件判断，一律假定"凡 `.jpg`/`.HEIC` 就是母片"。代理必然宁枉勿纵，于是把参考图也一并挡了。

**还必要吗：必要，不能删。** 它现在是唯一阻止原图被重新 `git add` 的机制——实测
`../data` 里只有 `.gitignore` / `LICENSE` / `README.md` / `photos`，**没有 CI、没有 workflow、
没有 pre-commit 钩子**（`gh api repos/huochemi/data/pages` 亦证实 Pages 是 `legacy` 分支直发）。

**但"开一条口子"是安全的**，因为参考图既不是母片、也不是派生物，它是一个**新类别**：

| 类别 | 可再生？ | 归属 | 与 `.gitignore` 的关系 |
|---|---|---|---|
| 母片（我拍的） | ❌ 不可再生 | `../photos-originals`（私有） | **被挡**（规则要的就是这个） |
| 派生档位 | ✅ 重跑即有 | data 仓 | 不被挡（后缀是 `_thumb.webp` 等） |
| **参考环境照** | ❌ 不可再生，但**可从来源重下** | data 仓 | **需要放行**（本方案新增） |

参考图是**内容**（像 `index.json` 一样：手工挑选、必须版本化、必须被服务），不是派生物；
规则对"第三类东西"误伤了，正确做法是**收窄口子，而不是删规则**。加这一条：

```
# 参考环境照（非母片）：放点位目录下的 refs/ 子目录，显式放行。
# 母片仍被上面的扩展名规则挡住——放行只作用于 refs/ 这一层子目录。
!photos/*/refs/**
```

**实测（临时仓库，未动真仓库）**——放行规则必须排在原有排除**之后**，结果：

| 路径 | 结果 |
|---|---|
| `photos/衡阳市-测试/refs/01.jpg` | ✅ 收录 |
| `photos/衡阳市-测试/refs/02.jpeg` | ✅ 收录 |
| `photos/衡阳市-测试/IMG_0001.JPG`（点位目录顶层） | ⛔ **仍被忽略（原图闸门完好）** |
| `photos/衡阳市-测试/DSC0001_thumb.webp` | ✅ 收录（现状不变） |

**这个口子为什么安全（三层，均已读代码/实测核实）**：

1. 放行被限定在 `refs/` 这一层子目录，**母片的实际落点（点位目录顶层）规则一字未改**；
2. 管线取媒体文件时**只读原图仓**（`preflightDir` 的 `mediaFiles` 来自 `ORIGIN_DIR`），
   即使有图混进 `refs/` 也不会被当成照片；
3. 一致性检查（孤儿派生图，`reportInconsistencies`）**只匹配 `_thumb.webp`/`_display.avif`/
   `_web.mp4` 后缀、不下钻子目录** ⇒ `refs/` 不会触发任何误报。

**改完之后复验（一条命令，只读，`git check-ignore` 不要求文件真实存在）**：

```
cd ../data && git check-ignore -v "photos/<任意点位>/refs/01.jpg" "photos/<任意点位>/IMG_0001.JPG"
```

期望：第一条**无输出**（已放行）、第二条输出 `.gitignore:<行号>:*.JPG`（母片闸门仍在）。
**改规则前在同一命令下的实测结果**（2026-10-07 于真仓库）：

| 路径 | 加放行规则前 | 加之后（临时仓实测） |
|---|---|---|
| `photos/衡阳市-测试/refs/01.jpg` | 被挡（`.gitignore:159:*.jpg`） | 放行 |
| `photos/衡阳市-测试/IMG_0001.JPG` | 被挡 | **仍被挡** |
| `photos/石家庄站/DSC05069_display.avif` | 放行 | 放行（不回归） |

**已评估但否决的两条替代路**：

- **让参考图走管线派生**（源图被现有规则自动挡在 git 外，只把 `_thumb.webp`/`_display.avif`
  入库）——否决理由：**那样源图谁都不存**（母片仓是"我拍的"真相源，不能进；data 仓被
  gitignore 挡住），换机器/重克隆后**无法重新生成**派生图，破坏 data 仓"里面的东西都能重跑
  出来"这条契约。参考图是内容，不是派生物，不该走派生通道。
- **存成 `.webp` 绕开忽略规则**——否决理由：① 实测本机 `sips` **不能写 webp**
  （`Error: Can't write format: org.webmproject.webp`；`sips --formats` 里 webp 无
  `Writable` 标记），要另装 `cwebp`；② "靠扩展名躲开规则"本身极脆，改天加一条 `*.webp`
  就静默失效。

### D6c 参考图的格式与尺寸纪律（`.gitignore` 放行后新增的必要约束）

**格式用 `.jpg`**（不是 webp）：理由见上（`sips` 不能写 webp）。

**尺寸压到展示尺寸再入库——这条不是省事，是纪律**：写进 git 历史的字节**永不回收**
（10-04 的教训：`git rm` 不等于减体积，只有重写历史才行；这也是当时决定把母片迁出本仓的
根本原因）。所以参考图必须在**入库前**压好。用真实照片实测的档位（源片 6.4 MB / 5472px）：

| 档位 | 体积 | 评价 |
|---|---|---|
| 1600px / q80 | **605 KB** | 太重（单张 = 现有 `_display.avif` 的 2.7 倍） |
| 1280px / q72 | 365 KB | 偏重 |
| **1024px / q70（推荐）** | **235 KB** | **与现有 `_display.avif`（实测 207–229 KB）同量级** |
| 900px / q68 | 182 KB | 更省，手机上看略糊 |

参考：现有管线产出的 `_display.avif` = 207–229 KB / 1920px、`_thumb.webp` = 23–26 KB / 300px。
⇒ 目标：**每张参考图 ≈ 200–250 KB**。一条系统命令搞定（无新依赖，`sips` 管线本来就在用）：

```
sips -Z 1024 -s format jpeg -s formatOptions 70 下载的图.jpg \
  --out ../data/photos/<点位>/refs/01.jpg
```

**命名定序**：`01.jpg` / `02.jpg` …，按文件名字典序 ⇒ **`01.jpg` 就是 marker 上显示的那张**。

**尺寸与版本的代价（如实记录）**：参考图**一档到底**——同一张图既当 marker 缩略图（浏览器
缩到 120px）又当 Lightbox 大图。所以首屏会为每个参考态点位多拉约 235 KB，而现有实拍点位的
marker 只用 23–26 KB 的 `_thumb.webp`。个位数点位无感（3 个点位 ≈ +0.7 MB）；涨到几十个
点位时需重新评估（见「风险」）。若将来要收，正解是给参考图也生成派生档位，而不是回到
"往 git 里塞更大的原图"。

### D7 不给参考图写 EXIF、不碰原图仓

- 原图仓的定义是"**我自己拍的**原片，不可再生的真相源"（`AGENTS.md` S1）。参考图进去
  会污染该事实源——以后无法靠它回答"哪些是我拍的"。
- `fix-gps.js` **没有"手填坐标"通道**（实测核对：只有锚点路"复制同组手机照坐标"与轨迹路
  "按时刻在 GPX 插值"；`GEO_MODES = new Set(['anchor','gpx'])`；`--plan-stdin` 的计划要求
  坐标与参照照片 EXIF 吻合到 1e-4 度）。要支持手填就得给持久化契约 `mode=` 加第三个取值，
  牵动 `docs/photo-metadata.md` 与 `test/geo-provenance.test.js` 的跨文件断言 ——
  **为一个不需要的能力去动契约，不值得**。
- 网图没有 EXIF `Make`/`Model` → `classifyDevice` 返 `null` → 每张都会进
  `unidentifiedDevices` 告警汇总；且"来源链接"EXIF 里没有承载字段，仍得另存。

## 升级路径：去过之后（零搬运、零删除）

到现场拍完照之后的**全部动作**：

1. 照片放进 `../photos-originals/photos/<同名点位>/`（原图仓，与实拍点位完全一样）
2. 一条命令：`npm run new-place -- "<点位>" --cover "<封面文件>"` —— 这就是**你建新点位本来
   就要跑的那条命令**（习惯不变）。对已存在的参考态点位，它只补一个 `index_photo` 键
   （`description`/`references` 一字不动，也不碰 `refs/`）；顺带保留它原有的好处：校验封面
   文件确实在原图仓里、不传 `--cover` 时列出候选清单
3. `npm run photos`（管线自动改为按封面 EXIF 取坐标、输出 `pinKind: 'photo'`）
4. 收尾：`rm -rf ../data/photos/<点位>/refs/`（参考图 + `point.json` 一起消失，见下）

对比甲方案的同样场景（搬 2 个字段 + 手工删 2 处 + 依赖同名匹配），丙**没有任何信息搬家、
也没有任何"要记得删的字段"**——`index.json` 从头到尾只被加了一个键。

**忘了第 4 步也无害、且不会静默**：实拍态管线**根本不读 `refs/`**（判定点是"原图仓有没有
媒体"，D1），所以点位照常出数据；同时管线会打一行 ℹ️ 提示"该点位已实拍，`refs/` 仍存在
（N 张），可删除"（只报告、不改退出码）。

### 参考图去留：留信息、删图片（并如实说明这一点不影响仓体积）

`description`/`references` 是**信息**（有长期价值，去过之后仍该留）；参考图是**他人作品的
搬运**，用途只有一个——"去之前熟悉环境"，去过之后使命完成 ⇒ **判据：留信息、删图片**。
这与 `docs/plans/2026-10-05-point-references.md` 的"只放链接、不搬运正文"是同一件事：
参考图本身就是那条纪律的**临时例外**，去过之后例外结束。

**需要说清的两点，免得对"删"有错误预期**：

- 删 `refs/` 的收益是"**不再对外提供**这组他人作品"（Pages 上 404），**不是"体积变小"**——
  写进历史的对象不会因为 `git rm` 而消失（10-04 已实证：`git rm` 152 张原图后
  clone 实拉量没变，是靠 10-05 把母片整体迁出 + 历史重写才降下来的）。所以"该压到 ≈200 KB
  再入库"（D6c）才是真正管住体积的那一步，删图只是收尾。
- 若将来想保留"当初的参考"作对比，正解是在**实拍态**抽屉里加一个「参考图」折叠区块——
  本方案**不做**（记为出界）。不做的话，`refs/` 留着也无人可见，只是对外裸挂着，
  两头不讨好。

## 风险

- **改动主管线是本方案唯一实质风险**：三处分支都在既有判定链上，其中 #1 是**放宽一条
  现有的整轮硬拦**（防搬家漏拷）、#2 还调整了 `preflightDir` 的校验顺序。缓解：判定条件由
  `index.json` + `refs/point.json` 显式决定（不是无条件放行）；实拍态的失败文案**逐字不变**
  （只是搬进分支内）；#1/#2/#3 各配单测；验收标准 9 要求"无参考态点位时输出逐字段不变"。
- **`new-place --cover` 的受控例外**：它原来对"已存在 `index.json`"恒硬拦（绝不覆盖人工
  内容），现在对参考态点位要改为**只补一个 `index_photo`**。风险是例外被写宽、某天覆盖了
  人工内容。缓解：条件写死为"已存在 `index.json` **且** 无 `index_photo` **且**
  `refs/point.json` 存在且坐标合法"，动作写死为"只允许新增 `index_photo` 这一个键，
  不允许改/删任何既有键"，并配单测覆盖"非参考态仍硬拦"。
- **`.gitignore` 放行口子**（本方案唯一触碰既有纪律文件的动作）：风险是"闸门被开大，母片
  又能进仓"。缓解：① 放行只作用于 `refs/` 一层子目录，母片落点（点位目录顶层）规则一字未改；
  ② **只追加、不改写**原有 4 条排除；③ 三层安全论证 + 验收标准 11 的复验命令（D6b）。
  ⚠️ 该仓**没有 CI 也没有 pre-commit 钩子**（实测），所以这条规则是纯约定，没有机器兜底
  —— 这也是它必须写得尽量窄的原因。
- **参考图是"写进历史就永不回收"的字节**：按 D6c 压到 ≈200–250 KB 入库，是唯一真正管住
  体积的动作。数量级：一个参考态点位 3 张 ≈ 0.6 MB 永久进入 data 仓历史（现 47.9 M）。
  20 个这样的点位 ≈ 12 MB（1 GB 的 1.2%），可接受；但**不要**把未压缩的 1080p 截图直接丢进去
  （单张就 600 KB，且删不掉）。
- **一档到底的代价（首屏 marker 流量）**：参考图同一张既当 marker（浏览器缩到 120px）又当
  Lightbox 大图 ⇒ 每个参考态点位首屏多拉 ≈235 KB，而现有实拍点位的 marker 只用 23–26 KB
  的 `_thumb.webp`。3 个点位 ≈ +0.7 MB、无感；涨到几十个点位 × 多张图时需重新评估 ——
  届时正解是给参考图也生成派生档位（那时才值得引入生成脚本），属**延后可做的优化**。
- **版权**：下载他人拍摄的照片属于个人参考用途的灰色地带。本方案**不热链、不镜像**，
  以 `references` 显式标注来源（用户 2026-10-07 主动提出"添加引用来源"）。⚠️ 如实说明：
  去过之后 `rm -rf refs/` 的收益是"不再对外提供"（Pages 404），**不是"抹掉痕迹"**——
  data 仓是公开仓，历史里的对象仍可按 SHA 取回（与 10-04 母片迁出后旧 blob 仍可达同理）。
  若将来要彻底移除，只有历史重写一条路。
- **`refs/` 与管线生成区同住点位目录**：靠"三层扫描都不下钻子目录"这一已核实的事实隔离
  （D6b）。风险是将来有人给扫描加递归 —— 缓解：该事实写进 `docs/photo-ops.md` 的参考图契约。
- 破坏性风险：**零**。本方案只新增文件、追加分支与追加一条忽略规则的**放行**（`.gitignore`
  本身不删除也不移动任何文件，见 `2026-10-04-data-repo-longevity.md` 同名小节）。
