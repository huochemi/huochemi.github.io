### 两个容易误判的点

1. **删照片不会回收仓库空间**。`.git` 694 MB > 当前发布内容 589 MB，多出来的就是历次
   "删旧换新"留在历史里的旧原图。不清历史，仓库只增不减。
2. **`.git` 不计入 Pages 的 1 GB**（Pages 量的是发布出来的文件），但它计入 GitHub 的
   仓库体积。所以这是两条独立的墙，**先撞的是 Pages**。

## 瓶颈（GitHub 官方限制，核对于 docs.github.com）

| # | 限制 | 数值 | 量的是什么 | 是否 per-repo |
| - | --- | --- | --- | --- |
| 1 | **已发布 Pages 站点** | **≤ 1 GB**（软） | 发布出去的文件（**不含 `.git`**） | ✅ 每个项目站点独立 |
| 2 | Pages 源仓库 | 推荐 1 GB | 仓库大小 | ✅ |
| 3 | 仓库本身 | 理想 <1 GB，**强烈建议 <5 GB** | 含 `.git` | ✅ |
| 4 | 单文件 | 50 MiB 警告 / **100 MiB 硬拦** | 单个文件 | ❌ **与拆 repo 完全无关** |
| 5 | 带宽 | 100 GB/月（软） | 站点流量 | 站点级 |

**形态 B 的处置与各条线的关系：**

| 线 | 现状 | 形态 B 之后 |
| --- | --- | --- |
| Pages 1 GB | **589 MB** → 约 **2~3 周**（按 25~40 MB/天） | 只剩衍生图 ~56 MB（47.3 webp + 8.6 `_web.mp4` + 元数据）→ **约 2 年**（AVIF 后 ~5,900 张） |
| `data` 仓（含 `.git`） | 694 MB | **694 MB 且不再增长**（新原图不再入库） |

| 带宽 | 未知 | 不变（Pages 站点仍是那一个） |

## 方案对比

### 路线 D：GitHub 分仓（**已选** = 形态 B）

**按用途拆，不按地点拆**：

- `data`（**保留原仓库名与 URL**）：只放衍生图 + `index.json` + 站点代码，继续做 Pages 站点
- `photos-originals`（**新建、私有、不开 Pages**）：只放原图，纯 git 存档

三个关键判断：

1. **原图仓不开 Pages** → 原图完全不占那 1 GB 站点配额。这是整条路线成立的枢纽。
2. **衍生图路径与 URL 完全不变**（仍是 `/data/photos/…`）→ 前端链接零改动、
   dev 代理零改动、`output.json` 结构零改动。
3. **原图仓的切分粒度（一个 / 按城市）是纯归档侧、可后置的决定**，不影响任何前端代码
   → **现在选"一个仓"不构成锁定**（详见「按仓库拆分」节的用户澄清）。

代价（如实）：三个 CLI 要支持双根、新增一个仓库、以及"跟免费额度赛跑"的性质不变。

### 路线 A：原图出 git（只留本机）—— 未选

零外部依赖、零费用；但原图会失去异地副本，需要自建第二份副本，且必须做一次破坏性历史
重写。**用户明确不买硬盘 → 本路线的前提不成立。**

### 路线 B：图片层外置对象存储 —— 未选

**首选 Cloudflare R2**（S3 兼容）：

| 项 | 免费额度 | 超出后 |
| --- | --- | --- |
| 存储 | 10 GB/月 | $0.015/GB·月（≈ ¥0.11/GB·月） |
| **出口流量** | **免费** | **永远免费** |
| 读请求 | 1,000 万次/月 | ¥2.6/百万次 |

**未选原因**：R2 的正式做法需要自定义域名（`r2.dev` 被官方标注"仅供非生产"、有限速），
用户已明确不买域名；且用户已明确不上云，R2 就只剩"托管衍生图"这点价值，而衍生图只有
47 MB。**整条路线留作远期备选（1 GB 真快满时再评估）。**

### 路线 C：腾讯云 COS / 阿里云 OSS —— 已排除

- 腾讯云公告（2024-01-01 施行）：**2024-01-01 后创建的存储桶，用默认域名访问对象时
  "任意类型文件不支持预览而是直接下载"**（服务端加 `x-cos-force-download: true` +
  `Content-Disposition: attachment`）
- 要能内联渲染图片，**必须绑自定义域名**；绑中国大陆地域必须 **ICP 备案**
- 阿里云 OSS 同类限制；**"不买域名"这条约束直接排除两家**

### 一路否决/不推荐的

- **把原图藏进 `_originals/`（Jekyll 下划线前缀不发布）**：只解决 Pages 1 GB，
  git 仓库那条线原封不动 → 不可持续
- **jsDelivr 当图床**：ToS 禁止把 jsDelivr 当通用图片托管（非库资产）
- **把图片层做成 Cloudflare Pages 项目**：图片仍在 git 里，GitHub 仓库线没解决
- **硬链接（原图同一份 inode 被两个仓库共享）**：看起来能免掉物理移动，但 **exiftool
  回写 EXIF 是"写临时文件再改名"，会打断硬链接**——而补 GPS 正是最常用的操作。
  两处副本会静默分叉 → **否决**
- **两个 git 仓库共用一个工作区**（`core.worktree` 指向同一目录）：`git clean -fdx`
  会删掉另一仓库的忽略文件（即原图）→ **否决**
- **把图片塞 GitHub Releases**：无 CDN 加速、不便版本管理，不如分仓
- ~~**只压衍生图（AVIF 替 WebP）**~~：不作为独立方案，但**已采纳为阶段 0 的顺手项**


> 修正记录：早先版本此处写的是 `3 → 55 → 56 → 53 → 117 → 299 → 335 → 374 → 478 MB`，
> 末值 478 与实测 HEAD 原图 533 MB 不符（该序列同样受"中文路径引号 + 未排除 `_web.mp4`"
> 两个口径问题影响）。以上为**重算后的值**。

| 每个 repo 的容量目标 | 一个 repo 能撑 | 每年要开几个新 repo |
| --- | --- | --- |
| 1 GB（GitHub 理想值） | ~5 周 | **~10 个/年** ← 不可行 |
| 2 GB | ~10 周 | ~5 个/年 |
| **4~5 GB（"强烈建议"上限）** | **~20~26 周 ≈ 5~6 个月** | **2 个/年** ← 可接受 |

### ⚠️ 修正（2026-10-05）：上表的增长率是"早期集中导入期"的最坏值，不是稳态

用户系统阐述了**产品定位**（已沉淀进 `docs/photo-workflow.md` 的「产品定位」节），
其中一条此前被忽略：**本产品增长是内容驱动的，不是时间驱动的。**

- 一个城市的拍车机位**有限且趋于收敛**，点位饱和后不再堆同质照片
- 新增只发生在"新内容"（新车型 / 新涂装 / 季节画面）时，**大量拍摄素材根本不入库**
- 所以 10.4 GB/年 反映的是早期集中导入存量照片的阶段，不是稳态

**推论**：若该定位成立，**原图总量会收敛到某个量级而非无限增长** —— 那么"每半年轮转"
很可能根本不会发生，轮转机制或许永远不需要启用。

**但"收敛到什么量级、多久到顶"目前只有定性判断、没有数据**（需积累数月的稳态增量才能
验证）。**在该数据出来之前，轮转阈值与轮转机制一并标记为"待定"，不在本期 scope。**

（注意：这不改变存量判断——已有约 608 MB 原图是既成事实，分仓仍须执行。）

## 按仓库拆分能否替代外置存储（2026-10-04 用户提案评估）

**用户提案**：不买硬盘、不用 R2，继续用 GitHub 存原图，形式为 ① 每城市一个 repo
② 每 dir 一个 repo ③ 一个 repo 存原图 + 一个 repo 存衍生图。

### 结论

**方向对，且 ③ 最接近正确形态（已采纳为形态 B）；① ② 拆错了维度。**
真正的枢纽是那条更简单的原则：**原图 repo 不要开 Pages 站点。**

### 用户澄清带来的修正（2026-10-05）

⚠️ 本节①的原始评估有一个前提被用户澄清掉了：原评估假设"city repo 里同时有原图和
衍生图"。**用户明确：衍生图无论属于哪个地理位置，都统一放同一个 repo；按城市 / 点位
拆 repo 只用于保存原图。** 据此修正：

- **若 city repo 只存原图**：不开 Pages 无意义、**不存在 "dir→repo 映射"**（前端只访问
  `data`，路径不变）、不占 1 GB 站点配额。此时它只是"**原图按地理切分**"，是一个**合理
  备选**——且按地理天然可无限追加，**永远不需要"封存/轮转"**（正好满足用户"不接受封存
  不可写"的要求）
- **若 city repo 同时存衍生图**（原始评估的情形）：**才是"方向偏了"**——它必须是 Pages
  站点 → 原图再次挤 1 GB 站点配额（等于把老问题复制 N 份）；且需维护 dir→repo 映射
  （新增 dir 忘登记或登错仓库名 → 图片链接指向不存在的地址 → **图裂**）

**"dir→repo 映射"是什么**（用户曾追问）：只有在"每个城市一个 repo 且该 repo 也是 Pages
站点"时才需要——前端得知道"南京这个 dir 的图片前缀是 `/data-nanjing/photos/…`"。形态 B
不存在这个问题：**所有衍生图仍在同一个 `data` 仓库、路径完全不变**；原图仓不参与任何
前端链接。

### 政策口径（如实说）

GitHub 官方原文：

- 仓库："We recommend repositories remain small, ideally less than 1 GB, and **less than
  5 GB is strongly recommended**."
- **"Git is not designed to serve as a backup tool."**
- 超额后果："you may receive a polite email from GitHub Support suggesting... putting a
  third-party CDN in front of your site... or moving to a different hosting service"

**判读：没有硬性禁止，有明确的"建议区间"，靠"是否影响基础设施"软执行。** 把每个 repo
控制在 1~5 GB、拆分得当，正落在推荐区间内 → 实际风险低。属于**"被容忍但不被推荐"**的
用法，可能的后果是一封建议邮件，不是封号。

### 相对代价（如实列出）

- `npm run photos` 等三个 CLI 要支持"原图在原图仓、衍生图在 data 仓"两处
- 仍属"被容忍但不被推荐"的 GitHub 用法——**用复杂度换零成本**，不是"解决了"容量问题
- 原图仓若未来真需要轮转，用户已明确**不接受"封存后不可写入"**（按地理位置组织，
  两年后仍可能回同一城市同一点位追加照片）→ 届时的替代是"按地理拆仓"（见上）

## 目标仓库形态

```
../data/                        ← 保留原仓库名与 URL，继续做 Pages 站点
  photos/<点位>/
    index.json                  ← 点位元数据（决策：留在 data 仓，见下）
    X_thumb.webp                ← 衍生
    X_display.webp              ← 衍生
    X_web.mp4                   ← 衍生（视频）
  .gitignore                    ← 新增排除原图扩展名
../photos-originals/            ← 新建私有仓库，不开 Pages
  photos/<点位>/
    X.JPG / X.HEIC / X.MP4      ← 原图（真相源）
  .gitignore                    ← 只忽略 .DS_Store 与衍生后缀（防误入）
```

**`index.json` 归属的决策**：**留在 `data` 仓**。理由：改动最小（新建点位时只有"原图
放哪"这一件事变化）、且 `process-photos.js` 的元数据读取路径不变。代价是新增点位时要
在两个目录各创建一次目录。（另一选项是随原图走；改变成本低，将来想换随时可换。）

## 双根管线改造要点

三个 CLI 当前都是单一根 `IMGS_DIR = path.join(__dirname, '../data/photos')`：

| CLI | 当前位置 | 读原图 | 写原图 | 读衍生 | 写衍生 |
| --- | --- | --- | --- | --- | --- |
| `process-photos.js:12` | `IMGS_DIR` | ✅（**改**） | ✖ | ✖ | ✅（不变） |
| `fix-gps.js:45` | `IMGS_DIR` | ✅（**改**） | ✅ EXIF 回写（**改**） | ✅ 审阅页缩略图（`fix-gps.js:563-571`） | ✖ |
| `delete-photo.js:28` | `IMGS_DIR` | 删（**改**） | 删（**改**） | 删（不变） | 删（不变） |

改造口径：

1. 各加 `ORIGIN_DIR = path.join(__dirname, '../photos-originals/photos')`；
   `IMGS_DIR` 保持 `../data/photos`
2. `process-photos.js`：**从 `ORIGIN_DIR` 读原图 → 向 `IMGS_DIR` 写衍生**；
   `index.json` 仍从 `IMGS_DIR` 读
3. `fix-gps.js`：EXIF 回写到 `ORIGIN_DIR`；审阅页缩略图仍从 `IMGS_DIR` 取
4. `delete-photo.js`：原图删 `ORIGIN_DIR`、衍生删 `IMGS_DIR`；**缺失即跳过**（沿用现有
   容错口径）
5. **启动预检**（遵守 S3：只预检一次、缺失即报错退出、不做兜底）：两个根都存在；
   点位目录只在一侧存在时 —— `data` 侧缺目录则**自动创建空目录**（无害），
   `ORIGIN_DIR` 侧缺目录则**报错退出并附提示**
6. `test/` 新增跨文件契约单测：照 `test/fix-gps.merge.test.js:126` 与
   `test/video-support.test.js:134` 的既有模式（源码正则解析常量 + 断言多处一致），
   锁住根的相对路径定义
7. 刻意**不抽共享模块**（沿用既有约定：三个 CLI 是独立 CLI），改一处要改三处

## 最佳实践参照：三层分离

照片归档的通行做法是 **3-2-1**（3 份副本、2 种介质、1 份异地）+ **母片/派生物分离**：

| 层 | 性质 | 该放哪 | 理由 |
| --- | --- | --- | --- |
| `index.json` / `output.json` / 站点代码 | 元数据 | **git（主站 / data 仓）** | 小、要 diff 与 review、要版本化 |
| `_thumb` / `_display.webp` / `_web.mp4` | **可再生** | `data` 仓 → Pages | 丢了重跑 `npm run photos` 就有 → **不需要备份，只需要托管** |
| 原图（母片） | **不可再生** | `photos-originals` 仓（私有） | 需要异地副本；GitHub 就是那条腿 |

**枢纽判断**：派生物可再生，所以它不配占用备份预算。现状恰好相反——把可再生的小文件
（6.8%）和不可再生的大文件（92.3%）一起塞进同一个仓库，两边都不讨好。

**阶段 1**
