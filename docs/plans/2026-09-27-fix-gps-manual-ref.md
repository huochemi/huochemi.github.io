# Plan：fix-gps 支持"手动指定参照"模式 + 交互中提示

状态：**已实现**（2026-09-27，验收记录见文末；本 plan 依 AGENTS.md 的 ADR 惯例永久保留）
日期：2026-09-27

## 1. 背景

`fix-gps.js` 的参照选择是全自动的：同文件夹内有 GPS 的照片按拍摄时间差排序，
从最近的开始逐张给预览，用户只能按 `n` 线性换下一个参照，**不能点名"就用某张"**。
当自动推荐的第一张不是正确地点、且候选较多时，按 n 挨个试很低效。

实际场景：`乌兰察布（集宁）/DSC04375.JPG` 缺 GPS，正确参照是
`IMG_5154.HEIC`（同文件夹，拍摄差 86 分钟），但自动推荐的是
`DSC04376.JPG`（差 33 分钟，地点不对）。

## 2. 需求

1. 交互流程中，在按键提示附近**就地提示**"自动参照不合适时可退出后手动指定参照重跑"，
   并给出可直接复制修改的命令实例——比去 README/docs 翻用法方便得多
2. 新增 CLI 参数，允许**手动指定目标照片和参照照片**，跳过自动推荐

## 3. 决策记录

已由用户确认：

| 决策点 | 结论 |
|---|---|
| `--ref` 是否跨文件夹 | **不允许**，仅限同文件夹。用户习惯：每个文件夹 = 同一地点/城市；若文件夹内没有带 GPS 的照片，会从手机导出一张当时在附近拍的照片放进该文件夹 |
| ref 文件没有 GPS | 报错退出，列出该文件实际状态（有 GPS 与否），防手滑写错文件名后静默失败 |
| `--target` 已有 GPS | 本次**报错退出**，不做覆盖模式（"坐标写错了要覆盖"是另一个需求，保持改动最小），报错文案说明原因 |
| 指定模式是否保留预览+确认 | **保留**（默认预览 + y 确认，与现有交互一致），另加 `--yes` 跳过确认 |

默认取值（review 时可改）：

| 决策点 | 默认取值 | 理由 |
|---|---|---|
| 提示显示频率 | 每张照片显示一次（dim 色，视觉不抢戏） | 会话只显示一次的话，提示滚走后遇到问题就没有上下文了 |
| 是否列出可用参照 | 本文件夹可用参照 ≤ 5 张时列出文件名，> 5 只报数量 | 帮用户"发现"该指定谁；数据已在内存，零成本 |
| `--target` 不带 `--ref` | 允许：只处理这一张，参照仍走自动推荐 | 同一条代码路径，顺带支持，方便"只修这一张" |

## 4. 交互设计

### 4.1 交互流程中的提示（每次候选展示时，按键提示行上方，dim 色）

```
── [1/1] 乌兰察布（集宁）/DSC04375.JPG  拍摄: 2026-08-15T09:28:23
参照: DSC04376.JPG  坐标: 41.040394, 113.087853  拍摄差: 33 分 30 秒
已在浏览器打开预览页；之后的照片请切换到浏览器按 Cmd+R 刷新。
自动参照不合适？可按 q 退出后手动指定参照重跑：
  npm run fix-gps -- "乌兰察布（集宁）" --target DSC04375.JPG --ref <参照文件名>
  本文件夹可用参照：DSC04376.JPG、IMG_5154.HEIC
看完两张照片后按键：[y] 确认复制坐标  [n] 换下一个参照  [s] 跳过这张  [q] 退出 >
```

- 命令实例中文件夹名与目标文件名用当前真实值填充，参照用占位符
  （脚本不知道哪张是对的），文件夹名统一加引号（含空格也不会错）
- "本文件夹可用参照"行仅在参照 ≤ 5 张时出现，> 5 张改为
  `本文件夹共 N 张照片带 GPS，可按 n 逐张查看`

### 4.2 文件夹内没有任何带 GPS 参照时（现直接跳过）

跳过文案追加一行（按用户习惯给出出路）：

```
[跳过] xxx/yyy.JPG：文件夹内没有带 GPS 的参照照片。
  可从手机导出一张当时在附近拍的照片放入该文件夹后重跑，或手动指定参照。
```

### 4.3 手动指定模式

```
npm run fix-gps -- "乌兰察布（集宁）" --target DSC04375.JPG --ref IMG_5154.HEIC
npm run fix-gps -- "乌兰察布（集宁）" --target DSC04375.JPG --ref IMG_5154.HEIC --yes
npm run fix-gps -- "乌兰察布（集宁）" --target DSC04375.JPG        # 不带 --ref：该张走自动推荐
```

流程：参数解析与校验（全部在进入交互前完成，出错即退出）→ 定位目标与参照 →
预览对比 → `y` 确认（`--yes` 跳过）→ 复用现有 `writeGps()` 写入 + 写入后验证 →
打印汇总。仍做全量扫描（需建参照池做校验），逻辑最简单。

## 5. 代码改动（仅 `fix-gps.js`，预计 40–50 行）

1. **参数解析**（~10 行）：`argv` 中第一个非 `--` flag 位置参数仍是文件夹
   （向后兼容 `npm run fix-gps -- 郑州`）；新增 flag `--target`、`--ref`、`--yes`。
   规则：`--target`/`--ref` 必须配合文件夹位置参数使用，缺了报错；
   `--yes` 只在指定模式有意义，单独使用报错
2. **校验**（~15 行，指定模式专用，按序检查，全部通过才进交互）：
   - 文件夹存在
   - `--target` 文件在文件夹中存在且**缺 GPS**（已有 GPS → 报错说明不做覆盖）
   - `--ref` 文件在文件夹中存在且**有 GPS**（无 GPS → 报错并列出实际状态）
   - `--ref` 缺省时：目标走现有自动推荐逻辑（复用候选排序代码）
3. **指定模式执行分支**（~15 行）：跳过逐张遍历，只处理 `--target` 一张；
   预览 → 确认（`--yes` 跳过）→ `writeGps()`（复用，含写入后验证）→ 汇总
4. **交互提示文案**（~5 行）：4.1/4.2 的两处 dim 色提示
5. 不抽取公共函数、不模块化 `normalizeExifDateTime`（现有复制注释已说明，保持现状）

## 7. 验收标准

1. `npm run fix-gps -- "乌兰察布（集宁）" --target DSC04375.JPG --ref IMG_5154.HEIC`
   （加 `--yes`）：DSC04375.JPG 的 GPS 写入成功且等于 IMG_5154.HEIC 的坐标
   （41.019867, 113.097519），写入后验证通过，汇总正确
2. 同上去掉 `--yes`：出现并排预览，按 `y` 后写入成功，按 `q` 退出不写入
3. 交互流程（`npm run fix-gps`）在按键提示上方出现 4.1 所示提示行，
   文件夹名/目标文件名为真实值；参照 ≤ 5 张时列出可用参照文件名
4. 错误路径均报错退出（exit 1）且文案清晰：文件夹不存在；`--target` 文件不存在；
   `--target` 已有 GPS；`--ref` 文件不存在；`--ref` 无 GPS；flag 缺少文件夹位置参数；
   `--yes` 单独使用
5. 向后兼容：`npm run fix-gps` 与 `npm run fix-gps -- 郑州` 行为与改动前一致
6. 测试验证方式：错误路径（4）可直接运行验证（均在进入交互前退出，无需 TTY）；
   验收 1–3、5 需在真实终端人工过一遍（交互依赖 TTY，无法脚本化）
