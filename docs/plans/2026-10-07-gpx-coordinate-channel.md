## 背景（自包含，零上下文可读）

### 现状

`npm run fix-gps` 是唯一的补坐标入口，机制是「**锚点复制**」：同目录内手机照自带原生 GPS，  
缺坐标的相机照按「拍摄时间最近的锚点」借坐标，写回原片 EXIF，并写溯源标记  
`GPSProcessingMethod = hcm-geosource ref=<参照文件名> date=<YYYY-MM-DD>`。

用户 2026-10-05 起改用 **Apple Watch「户外步行」记录轨迹**、用手机上的 gpx export 导出 `.gpx`  
到点位目录。这引入第二条坐标来源：**按拍摄时刻在轨迹上插值**（业界 geotag 的事实标准，  
exiftool `-geotag` / Lightroom 地图模块 / darktable(Ansel) 同一套逻辑）。

## 第二轮修订（2026-10-07 晚，用户批准「路线 2」）

第一轮实现上线后，用户对 `--gpx` 的**落空处置**提出质疑（原话："我还以为只是给一些照片
补坐标，所以有多少参照就补多少，看起来这像是 validation 而不是 fix"），并指出
`--gpx` 与 `--review` **参数不对称**。复盘后确认这是本 plan 的**内部自相矛盾**：

| 原条款 | 原文 | 隐含要求 |
| --- | --- | --- |
| 判据 4 | 「排他粒度 = **照片级**」「混合点位是合法状态」「照片级幂等」 | 逐张处理 |
| 阶段 6 | 「窗口内 4 张走 GPX、窗口外 8 连拍走锚点」 | 同目录混合 |
| 验收 1 | 「先跑 `--gpx` 再跑锚点路与反序**逐字节相同**」 | **预设 `--gpx` 只写一部分** |
| 验收 6 | 「有落空照片即不写任何文件」 | **整批失败** |

**验收 1 与验收 6 直接互斥**：混合点位必然有落空照片，按验收 6 就是退出、零写入，那"顺序
无关"退化成"两次都没写"，验证不了任何内容。硬对照：锚点路的 `runPlan` 对"部分目标已带
坐标"是**跳过那些、写其余**、从不整批罢工 ⇒ **两条通道对同一类情况给了相反处置**，是实现
一致性缺口而非纪律。故实施**四处修订**：

### 修订 A · 落空处置改「能补就补」（推翻原验收 6）

- **窗内的写、窗外的逐张打印后跳过**，**不整体失败**。窗外是日常现象（手表晚按几分钟才
  开始拍、或拍完才结束记录），不是错误
- 安全性**不放松**：时区判错的证据是"手机照能否落窗内"，由**时区判据自己**拦
  （calibrators 为空 / 没有任何整数小时偏移能把手机照放进窗内 → 报错）；而"有些 target
  落窗外"**不是**时区错的证据（故不再拿它当第二道闸门）
- 收尾提示把窗外的交给锚点路（`fix-gps:anchor -- <点位> --review`）
- **顺带解决**"混合点位跑不完"：`--track` 写窗内 → `--review` 里那些变 `done` 灰条 →
  只剩窗外走锚点。无需再手工移文件（第一轮的验收 4 就是被这个整批闸门逼出来的绕路）

### 修订 B · 命名分路（`--gpx` → `--track` + 脚本名）

- **问题的根因**：8 个参数里只有 `--gpx` 在回答"**用什么**"（坐标来源），其余全在回答
  "**怎么做**"（`--review`/`--all`/`--target`…）——一个在"来源"维、一堆在"操作"维，不成对
- 锚点路其实**一直没有名字**：它靠 `--review` 等**操作**参数间接露脸
- 修法：给两条路各一个**平级的来源名**，并显式落到脚本名
  - `--gpx` → **`--track`**（通道名从"数据格式"改成"数据实体"；将来支持 `.fit`/`.tcx`
    不必再改名。代码里本就有 `TRACK_EXTS`，一致性更好）
  - 新增 **`--anchor`**（锚点路的显式写法，可省）
  - `package.json` 新增 **`fix-gps:anchor` / `fix-gps:track`** 两个脚本（= 预设裸 flag 的
    快捷方式）；`fix-gps` 保留为通用入口，默认锚点路（**零迁移**，现有命令原样能跑）
  - **通道判定点唯一**：出现 `--track` 即轨迹路，否则锚点路；`--anchor` 与 `--track` 互斥
- ⚠️ **EXIF 里的 `mode=gpx` 是持久化契约，不随参数改名**（已写入的原片无法回填）
- `--plan-stdin` **通道无关**：通道由计划 JSON 的 `mode` 字段判定（单一判定点）；故命令行
  再指定 `--anchor`/`--track` 会被拒绝。两条路导出的计划走**同一个**写入入口
- 旧名 `--gpx` 仍在终端历史里 → 给出**明确迁移指引**（含"新名 `--track`、`mode=gpx` 不变"），
  不退化成"文件夹不存在"（与 `--plan` 的处理同例）

### 修订 C · 轨迹审阅页（`--track --review`，用户选「路线 2」）

第一轮判据 ② 说"轨迹路不共用 `--review`、无图形页面"。用户追问"为什么没有
`fix-gps:track -- 石家庄站 --review`"，复盘发现漏了一个**真实决策项：排除某张**——用户在
地图上一看某张落点明显不对，应当能在页面上把它剔除。于是轨迹路**也升级成审阅页**：

- **页面内容**：高德底图 + 轨迹折线（`AMap.Polyline`）+ 相机照插值落点（**按拍摄时间
  编号**，"顺序是否往回跳"是关键信号）+ **手机锚点照**（唯一外部真值，用来判断轨迹本身
  准不准、相机时钟有无整体偏）
- **可操作**：勾选/排除某几张 → 「复制写入命令」→ 回终端 `--plan-stdin` 一次写入
- **同名 `--review` 是刻意的**：两条路都"要你审阅并拿主意"，页面内容不同是因为**可决策的
  东西不同**（锚点路=挑分组/改投；轨迹路=核对几何分布/排除）。判据 ③ 的"分层原则"
  （顶层来源维 / 底层操作维）在此闭合
- 模板：`fix-gps-track-review-template.html`
- ⚠️ **相机照的点必然落在轨迹线上**（坐标就是插值算出来的），单看"点在不在线里"看不出
  绑错；能暴露绑错的只有"**顺序错乱**"（点沿轨迹往回跳）与"**整体平移**"（偏离手机锚点
  同一侧）两个信号——这正是页面必须画"编号落点 + 手机锚点照"而非只画轨迹的原因

### 修订 D · 轨迹计划写入（`--plan-stdin` 支持 `mode:"gpx"`）

- `runPlan` 按计划 JSON 的 `mode` 分派：`mode:'gpx'` → `runTrackPlan`；缺 `mode` → 锚点计划
- 轨迹计划格式：`{ dir, mode:'gpx', track, tz, assignments:[{file, lat, lng}] }`
- 校验链：轨迹文件名一致 + **重算插值坐标与计划一致**（`PLAN_COORD_EPSILON`，防页面开着太久
  后轨迹/时区被改）+ 目标当前缺坐标（幂等）；写入走 `writeGpsFromTrack` 的逐张验证

## 目标与非目标

**目标**：让 GPX 成为一条**独立、可判别、顺序无关**的补坐标通道，且与锚点通道**可按照片共存**  
而不互相污染。

**非目标（界外清单）**：

1. **不改**存量 17 个点位的已有坐标（EXIF 已写死，回改不可逆）
2. **不做**基准照机制（决策 ④）；**不做**相机时钟偏移的自动标定（理由见判据 3）
3. **不改**点位代表坐标的口径（仍取封面坐标）
4. **不改**缺坐标硬拦口径（组内任一张缺 → 整组不产出）
5. **不加** `index.json` 豁免清单（2026-10-03 已定）
6. ~~**不做** GPX 路的图形核验页（第一阶段只做终端报告；页面留作后续独立议题）~~
   → **第二轮修订推翻**（修订 C）：用户要求"在地图上把 gpx 路线显示出来"，已实现
   `--track --review` 审阅/排除页
7. **不做**「锚点质量闸门」（用隐含速度 / 距轨迹距离筛坏锚点）—— 这是**独立议题**，  
   需另开 plan；本 plan 只在石家庄站收尾里对该点位已知的坏 fix 做数据处置
8. **不动** `AGENTS.md` 既有条款（除完成后按流程 3 处理「路由」，且仅当新建域文件时才加行）

## 关键判据（本 plan 的核心）

### 判据 1：锚点池 = 设备维度，而非「有无坐标」

三态取代原来的二态：

| 状态       | 判据                                    | 在锚点页的角色                   |
| -------- | ------------------------------------- | ------------------------- |
| `anchor` | `classifyDevice === 'phone'` **且**有坐标 | 可被选作参照                    |
| `target` | **无坐标**（不论设备）                         | 待补坐标的待办                   |
| `done`   | 有坐标 **且** 设备不是手机                      | **只读灰色历史条，无任何交互控件**（新增状态） |

⚠️ 「已带坐标的相机照」（`done`）是本次新增的第三态：它**既不能进锚点池**（会污染），  
**也不能进待办**（已修好）。第一条路跑完后，它的产物在第二条路的页面里必须**可见但不可选**。

**未知设备 = 硬错**：扫描阶段只要有一张照片 `classifyDevice` 返回 `null`，立即报错退出。  
报错内容须含：**文件名 + 原始 `Make`/`Model` + 去哪加映射**  
（`process-photos.js` 的 `CAMERA_MAKES` / `PHONE_MAKES`，**并提示 `fix-gps.js` 也有一份副本要同改**）。

### 判据 2：来源通道（`mode=`）

写入形态：

```
hcm-geosource mode=anchor ref=IMG_5858.HEIC date=2026-10-07
hcm-geosource mode=gpx    ref=Walking 2026-10-06T112533Z.gpx date=2026-10-07
```

- 取值集合**最小化**：`anchor` | `gpx`（将来要细分再加 —— 加维是向后兼容的增量）
- ⚠️ **`mode=gpx` 是 EXIF 持久化契约，不随命令行参数改名**：CLI 的 `--gpx` 已改为
  `--track`（修订 B），但写入端仍写 `mode=gpx`（`GEO_MODES` 只认 `anchor`/`gpx`）
- **缺 `mode=` ⇒ 视为 `anchor`**。这不是 fallback，是**准确的历史陈述**：2026-10-03 至  
  2026-10-07 之间写入的全部坐标都只有锚点这一条路可走。该理由必须与代码注释、docs 同处留存
- 解析改造：新增 `parseGeoTag(raw) → { mode, ref } | undefined`；  
  `parseGeoSource(raw)` 改为 `parseGeoTag(raw)?.ref`，**保持返回字符串的旧语义不变**  
  （`output.json` 的 `geoSource` 字段形态不变）
- `output.json` **不新增** `geoMode` 字段（2026-10-07 用户拍板）：它是可从 `geoSource`
  推导的冗余副本且无消费者；将来需要时解析 `geoSource` 即得，不存在"现在不存以后补不了"

### 判据 3：时区（可自动定准）与相机时钟（不可自动定准）

**信噪比结论（本 plan 的关键判断）**：

| 待定参数       | 搜索粒度 | 1 单位偏移对应的位置误差                  | 与 GPS 噪声（30–50 m）比 | 结论         |
| ---------- | ---- | ------------------------------ | ------------------ | ---------- |
| **时区**     | 整小时  | 走动 0.44 m/s ⇒ **1 h ≈ 1584 m** | 高 30 倍以上           | **可自动定准**  |
| **相机时钟偏移** | 秒    | 1.4 m/s ⇒ **30 s ≈ 42 m**      | 同量级                | **不可自动定准** |

⇒ **时区**：枚举整数小时偏移 `h ∈ [-12, +14]`，判据为  
**①使尽量多的照片落入轨迹时间窗；②窗口内数量并列时取平均残差最小者**。  
（轨迹仅 55 min 时，错误的小时偏移会让**全部**照片落窗外 —— 信噪比极高。）  
必须满足「该目录存在**原生坐标**的手机照」（即 `geoSource` 为空且有坐标）；判定结果  
**显式打印依据**（如「按 10 张原生手机照交叉验证，时区 = UTC+8」）；`--tz` 可覆盖；  
**若无可用于校准的原生照片 → 报错退出并要求显式 `--tz`**（fail-early，不静默推导）。

补充自检：若**全部照片落窗外**，且存在某个整数小时偏移能把它们全部拉回窗内 ⇒ 报  
「**疑似时区差 N 小时**」，而不是报「这些照片缺坐标」。

⚠️ **已知坑（必须避开）**：不要用「按经度推时区」（`round(lon/15)`）——  
中国全境统一 UTC+8，而乌鲁木齐经度 87.6° 会被推成 UTC+6 ⇒ **必然出错**。

⇒ **相机时钟**：**不做自动标定**（决策 ④）。改为在报告里打印每张照片的  
「坐标到轨迹的横向距离」与「距轨迹端点的时间」；若**全部照片系统性偏向轨迹同一侧**  
则给出「疑似相机时钟偏差」提示（用**可见性**代替规则）。

### 判据 4：混合点位是合法状态

- 排他粒度 = **照片级**（同一张照片不能被两条路各写一次），**不是目录级**
- 照片级幂等：目标照片已有坐标 ⇒ 跳过，并**显式打印「因已有坐标而跳过 N 张」**
- `npm run photos` 收尾汇总里，对「含 ≥2 种来源」的点位打印一行提示（**不阻断构建**）
- ⚠️ 混合点位下「点位坐标 = 封面坐标」变得**偶然**（换封面会移动 marker）——  
  这是已知性质，写进 `docs/photo-metadata.md`，**不改口径**

## 风险（2026-10-07 复盘：原「未决」第 1 条 geoMode 已由用户拍板删除，无未决项）

1. **风险**：相机时钟偏移无法自动标定 ⇒ 轨迹路的精度上限由「用户手动对准相机时间」决定（决策 ④）
2. **风险**：一条轨迹无法覆盖整天 ⇒ 同一点位多次拍摄需多个 `.gpx`；第一阶段
   **>1 个 `.gpx` 即报错要求处置**，多轨迹合并留作后续
3. **已定**：多 `<trkseg>` 的 `.gpx` 语义 = **按时间序拼接**为一个点序列（`parseGpxTrack`
   返回 `segCount`；若拼接后出现时间回退则置 `reordered` 并在报告里提示）
4. **UX 提醒**：`--plan-stdin` 是**通道无关**的（通道由计划 JSON 的 `mode` 判定），故
   `fix-gps:anchor -- <点位> --plan-stdin` / `fix-gps:track -- <点位> --plan-stdin` 会被
   `parseArgs` 拒绝（报错已说明理由）。写入命令一律用通用入口 `npm run fix-gps -- <点位>
   --plan-stdin`——审阅页「复制写入命令」给的就是这个
5. **纪律提醒**：本 repo 常有并行会话改同一工作区；提交前须重看 `git status` 与 `git diff`
