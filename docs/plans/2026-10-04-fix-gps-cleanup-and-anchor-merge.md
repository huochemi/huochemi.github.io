前置：`docs/plans/2026-10-03-fix-gps-review-page.md`（审阅页 + `--plan-stdin` 的原始设计）

## 背景与动机

`--review` 审阅页在 2026-10-04 的十轮迭代后，功能已稳定，但留下三类不一致（审计结论，均有代码位置为证）：

1. **工具在教用户走已被淘汰的流程**：导出桥早已从 `pbpaste | ... --plan-stdin` 改为
   页面直接复制"一行完整命令"（JSON 内嵌），但 6 处引导文案没跟着改，其中 3 处
   运行时可见——用户照做会踩"剪贴板单槽竞争"（复制 JSON 后再复制命令文本会覆盖它）。
2. **无人使用的平行入口**：`--plan <file>`（从文件读计划）在用户明确表示"不需要
   临时文件"后没有任何引导使用，是纯粹的维护面。
3. **模型冗余**：每张原生 GPS 照片被立为独立分组，同位置连拍的多张锚点各自成组，
   产生 0 张空组、组色断裂、"0.5 秒之差该归谁"的伪问题。用户连续三轮追问（绿徽章
   撞色 / 紫夹青绿 / C 还是 D）都指向这一条。

## 设计

### 1. 清理 `pbpaste` 残留引导（6 处）

统一改为一行的命令形态：`echo '<单行 JSON>' | npm run fix-gps -- "<文件夹>" --plan-stdin`。

| 位置 | 现状 | 改为 |
|---|---|---|
| `fix-gps.js` `runReview()` 收尾打印（运行时可见） | `pbpaste \| npm run fix-gps -- …` | 文字引导："点「复制写入命令」→ 回终端直接粘贴回车 → 按 y"（不再打印示例命令，页面给的才是权威） |
| `fix-gps.js` `printUsage()`（运行时可见） | 同上 | `echo '<分组计划 JSON>' \| npm run fix-gps -- 文件夹 --plan-stdin` |
| `fix-gps.js` `--plan-stdin` 无管道报错（运行时可见） | 示例用 `pbpaste` | 示例用 `echo '…' \|` |
| `fix-gps.js` 文件头注释 | 同上 | 同上 |
| `fix-gps-review-template.html` 顶部注释 | `pbpaste \| …` | 一行命令形态 |
| `docs/photo-metadata.md` | `--plan <file>` / `--plan-stdin` | `--plan-stdin`（含文件入口删除后的表述） |

### 2. 删除 `--plan <file>` 入口

保留 `--plan-stdin`（用户已明确：复制命令 → 粘贴 → 看结果，不落临时文件）。

- `parseArgs`：删 `--plan` 分支、`args.plan` 相关校验（`--yes` 准入条件、互斥校验、
  "只能二选一"）、错误文案里的 `--plan` 字样。
- `readPlanJson`：只保留 stdin 分支（函数可内联或改名 `readPlanFromStdin`）。
- `main()`：`args.plan || args.planStdin` → `args.planStdin`；`sourceDesc` 不再需要两态。
- `printUsage` / 文件头：删 `--plan groups.json` 行。
- 模板第 4 区块 `renderPlan()`：删 "# 也可把 JSON 存成文件后用：… --plan groups.json" 注释行。
- **代价（明示）**：失去"计划落盘、编辑器改完再写"的路径。`--yes` 仍可用于 `--plan-stdin`。

### 3. 同位置锚点合并（核心）

**判据**：两锚点直线距离 < `ANCHOR_MERGE_METERS = 5` 米即视为同一处。选 5 m 而非
"坐标完全相同"，因为同地点隔几分钟连拍时手机 GPS 会有数米漂移，逐字节判据会让
同一处重新裂开。5 m 远小于任何决策粒度（本例两处相距 114 m），也远小于 GPS 自身误差。

**双源一致性（必须同改）**：`process-photos.js` 的 `describeAnchorSpread()` 目前用
`toFixed(6)` 坐标完全相同来数"落在几处"。改为同一 5 m 判据，否则 photos 的提示与
审阅页的分组会互相矛盾（P3）。该常量在两个脚本各存一份，注释互相点名——两个脚本
都是独立 CLI，不引入共享模块（避免为 1 个常量做架构改动）。

**合并发生在 `fix-gps.js` 的数据层**（`scanDirForReview` 之后、`runReview` 组装 data 之前）：
分组结果作为 `anchors` 输出，每组带 `members`（组内全部锚点文件名）。

```json
{ "file": "IMG_5815.JPG", "lat": 31.971153, "lng": 118.789611, "time": "…",
  "kind": "anchor", "geoSource": null, "members": ["IMG_5815.JPG","IMG_5816.JPG","IMG_5817.JPG","IMG_5818.JPG"] }
```

- **代表** = 组内拍摄时间最早的一张（本例 IMG_5815）；坐标用它自己的，不取平均
  （不引入"新坐标"概念，写入结果可逐字节对照）。组坐标分歧 ≤ 5 m，属 GPS 噪声级。
- 模板侧：`anchors` 即分组，`label()` / `gColor()` / `anchorIndex()` 全部基于分组；
  另建 `file → 分组` 映射，让胶片条里每张锚点照片显示**它所属分组的颜色**——这正是
  "同一处的四张锚点同色、不再切断时间轴"的来源。
- 标签仍用 A/B/…（合并后组数变少，键盘 `A`–`E` 改投、归属条、图例全部照旧），
  分组卡片显示"位置 A · IMG_5815 等 4 张"以表明"处"的含义。
- 连带效果：`renderSplit()` 分界滑杆此前"仅恰好 2 锚点时出现"——你的真实数据是
  5 锚点，从未可用；合并后 2 组，滑杆变成主力控件。
- 已写入的 `geoSource` 标记不重写（历史溯源保持原样，记录的是当时的参照）。

## 实现后修订（2026-10-04）

1. **阈值语义是严格小于**：相距恰好 5.00 m 的两张锚点**不**合并（`<` 而非 `<=`）。
   实测边界：3.34 m 并入、5.00 m 不并入、8.90 m 独立、114 m 独立。
2. **链式邻近会连锁合并**：A-B 4 m、B-C 4 m（A-C 8 m）→ 三张同为一组（并查集）。
   这是刻意的：同地点走动时逐步漂移的连拍不应被拆散；代价是极长的漂移链理论上
   能"串"起超出 5 m 的跨度，但同一文件夹内的锚点都来自同一次拍摄，风险可忽略。
3. **`describeAnchorSpread` 同步改判据**（原为 `toFixed(6)` 逐字节比对）：两侧现在
   都按 5 m 聚类，实测同一批锚点在 photos 提示与审阅页分组里说法一致。
4. **旧命令 `--plan <file>` 的报错专门优化**：用户终端历史里可能还留着旧命令，因此
   `parseArgs` 对它给明确指引（"已移除，请用审阅页复制写入命令"）而不是退化成
   "文件夹名不存在"。
5. **验证证据**（隔离副本 `/tmp/hcm-verify`，用真实照片 + 两张合成锚点）：
   - 合并：4 张锚点 → 3 处（3.34 m 并入 A、8.90 m 独立成 B）；删掉合成点后
     3 张 → 2 处，分界滑杆出现、统计 `A 6 张 · B 9 张`（无 0 张空组）、组内两张
     锚点同色（#378add）、plan 的 ref 为组代表、targets 合计 15。
   - 页面（jsdom 真实 DOM）：非代表的组内成员显示所在组的颜色与「📍 原生 GPS ·
     位置 A」徽章；归属条 3 个按钮、当前所属高亮；键盘 `a`/`c` 改投实时反映到
     plan JSON；悬停照片卡片 → 密度条对应柱加白描边；位置分布图按处绘制。
   - 写入链（真实 pty，`--plan-stdin`）：按 `y` 写入并验证、0.7s 退出；按 `q`
     放弃且 EXIF 复查确认零写入、0.5s 退出；`--yes` 免确认 0.3s 退出——**上一轮
     修的 /dev/tty 挂起 bug 未回归**。
   - `--plan <file>`：报错"已移除"+ 指引，退出码 1。
6. **用户已把 `南京南站附近1` 改名为 `南京南站东南角`**（写入坐标之后的操作），
   且该文件夹现有内容是 17 张（2 张锚点：IMG_5817.JPG 在 14:29、IMG_5820.HEIC 在
   14:34，相距 114 m）。本计划的验证因此改用该文件夹；早先会话里"5 张锚点"的记录
   是改名前的状态，plan 文档按 P1 保留原样不改。
