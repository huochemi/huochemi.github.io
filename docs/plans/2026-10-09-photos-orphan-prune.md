## 背景（自包含，零上下文可读）

站点是火车迷的照片地图，一个点位 = data 仓的一个目录。**原图**（真相源、不可再生）在
`../photos-originals/photos/<点位>/`；**派生图**（可再生：`_thumb.webp` 300px /
`_display.avif` 1920px / 视频 `_web.mp4`）与 `index.json` 在 `../data/photos/<点位>/`。

删除照片有两条路：

| 怎么删 | 原图仓 | data 仓派生图 | 结果 |
|---|---|---|---|
| `npm run del-photo -- "<点位>" "<文件名>"` | 删 | **一起删** | 干净 |
| 在 Finder / 终端里手工删原图 | 删 | 留着 | **派生图成孤儿** |

`npm run photos` 末尾有一段「数据一致性检查」（`process-photos.js` 的
`reportInconsistencies`，约 472–549 行），它的**配对基准**是原图仓顶层的原片清单
（`ORIGIN_DIR/<点位>` 的 `fs.readdir`），找出"data 仓里有派生图、原图仓却没有对应原片"的
文件，**只报告、不删除**，末尾附一行可自行复制的 `rm` 命令。

实际症状（2026-10-07 实测，全 20 个点位扫过一遍）：

- 只有 `南京长江大桥玻璃栈桥` 有孤儿：**102 个文件 / 7.34 MB / 涉及 51 张照片**
  （原图仓现存 40 张、data 侧 91 组派生图，91 − 40 = 51，对得上）；其余 19 个点位干净。
- 该点位**从未提交进 git**（data 仓与原图仓里都是未跟踪状态）⇒ 清掉不涉及历史重写、
  不影响仓库体积。
- 打印出来的那条 `rm` 是 102 个绝对路径拼成的 7 KB 长串 —— 不好用，也容易看漏。

## 根因：报告是好的，"只报告"在规模化后不再够用

`reportInconsistencies` 的"只报告"是 2026-09-30 的有意设计（决策见
`2026-09-30-photo-deletion-workflow.md`）。当时它是**安全的**，因为判定基准里
"目录读不到"和"目录里没有原片"被写成了同一个结果 —— 空清单：

```js
try { files = await fs.readdir(originPath); }
catch { /* 原图仓缺该目录：基名为空，下面会如实报孤儿——那是真问题，不该静默 */ }
```

只报告时，这个"空"最坏只是多打印几行，没代价。**风险是在"把这段为报告设计的容错直接接到
删除动作上"时出现的**：同一个"空"会变成"这个点位的派生图全都多余，可以删"。

### 决定性证据：同一信号在管线内部有两种相反解释（2026-10-08 实测）

拿**逐字复制**的真实管线（只把两个目录常量指向 `/tmp`，其余一行未改）跑"该点位目录读不到"
场景（对目录 `chmod 000`），输出如下：

```
⏭️ 1 个文件夹未通过预检，本轮不产出数据：
  P：原图仓中读不到点位目录: EACCES: permission denied, scandir '/tmp/cdemo/origin/P'
    确认 /tmp/cdemo/origin/P 存在且可读后重跑：npm run photos

⛔ 没有任何文件夹通过预检，保留原有 output.json 不予覆盖。

数据一致性检查：
  ❗ 发现 6 个孤儿派生文件（无对应原图，会随 data 仓库一起部署）：
    P/IMG_1_display.avif / P/IMG_1_thumb.webp / P/IMG_2_display.avif
    P/IMG_2_thumb.webp / P/IMG_9_display.avif / P/IMG_9_thumb.webp
```

`IMG_1` / `IMG_2` 的原片**好端端躺在那个目录里**（只 `chmod 000`，什么也没删），却被列为
"可删"。两条关键事实：

1. **预检对文件夹级失败只做"打印一行 + 跳过该点位"，程序继续往下跑**（这是有意设计，
   注释写明"一次运行即可看到全部有问题的文件夹"）；退出码 1 是整轮结束时的返回值，
   **不是在报错处停的**。
2. 决定"哪些文件该删"的是**最后那一步**（一致性检查），而它把同一个读取失败吞成空清单。

⇒ 若把删除挂到后一种解释上，**同一次运行会既叫你"确认后重跑"，又自动删掉好图**。误判粒度
是**整个点位**（基准按点位目录整份算），不是一两张。

## 决策：选 C + 两道硬闸门（用户拍板）

| 方案 | 做什么 | 误删风险 | 结论 |
|---|---|---|---|
| A 只改纪律（一律走 `del-photo`） | 不写代码 | 无 | 否：连删几十张要粘几十次命令 |
| B 管线加 `--prune`，新增 `npm run photos:prune` | 独立命令按需清理 | 低 | 否：日常仍要"记得敲一条"（被 C 取代） |
| **C（选定）`npm run photos` 跑完自动清理 + 两道硬闸门** | 零记忆负担 | 低（闸门兜底） | **是** |
| C 无闸门 | 自动清理 | **高**：读取失败 ⇒ 整点位好图被删 | 否（就是上文实测的坑） |
| E 站点仓 pre-push 检查孤儿 | 有孤儿就拒绝推送 | 无 | 否（可叠加）：**晚一步**——data 仓先提交先推送，拦站点仓时孤儿已上线 |

C 的"读不到就停手报错"正是用户 2026-10-08 的反馈推出来的：**"不退出，下面还得区分权限问题
还是文件夹下面确实没有文件 —— 那为什么不退出？"** 这道闸门不引入任何"区分权限 / 真空"
的下游判断逻辑（那正是要被消灭的东西），只加一行：**读失败 ⇒ 本轮零删除 + 报错退出**。

### 撤回的两条（用户判定为 over engineering，2026-10-08）

曾把"原片换成 RAW（`.CR3`/`.DNG`）"与"原片被移进子目录"列为"认不出 ⇒ 判 0"的成因。
用户否掉：**"我为什么要把 RAW 放进来，我为什么要把文件放在子目录？"** 采纳 —— 这两条
不为此设计任何东西。撤回后，真正站得住的论据只剩**一条**：读取失败被吞掉。

## 实现方案

### D1 判定与动作：顶层自动清理，`refs/` 一层**维持只报告**

| 层 | 配对基准（原图仓） | 行为 |
|---|---|---|
| 点位目录**顶层**（实拍态派生图） | `ORIGIN_DIR/<点位>` 顶层，白名单 `ALLOWED_EXTS` | **自动清理**孤儿（+ 两道闸门） |
| `refs/` 一层（参考态派生图） | `ORIGIN_DIR/<点位>/refs/`，`REF_IMAGE_EXTS` | **只报告**（现状不变，末附 `rm` 文本） |

`refs/` 不并入自动清理的理由：`refs/` 目录**不存在**是**正常态**（实拍态根本不用参考图），
而顶层目录不存在几乎必是异常。要对 `refs/` 自动清理，就得再区分"ENOENT（正常，可清）"
与"EACCES（异常，停手）"—— 又是一套失败分类，正是本次要消灭的东西。⇒ 一条清晰的边界：
**自动清理只管一个有明确前置条件的目录；`refs/` 继续只报告。**

### D2 两道闸门（任一命中 ⇒ 本轮**零删除** + 退出码 1）

按用户口径：**不做"部分点位照删"的分支**，命中即整轮停手 —— 少一条规则，少一处判断。

| 闸门 | 触发条件 | 含义 | 输出（`⛔` 红） |
|---|---|---|---|
| 一 · 读失败 | 任一点位的**顶层原图目录** `fs.readdir` 抛错 | 无法确认哪些派生图是多余的（实测的那种坑） | 列出点位 + 原始错误，提示"确认存在且可读后重跑" |
| 二 · 会删空 | 某点位顶层**全部**派生文件都是孤儿（该点位将被清空） | "整组下线"是另一个量级的决定，值你看一眼 | 提示手动整组下线 + 可复制的 `rm -rf`（两处目录） |

闸门二沿用 `del-photo` 既有的「删后为空」纪律（`docs/photo-ops.md`）：整组下线走手动删目录，
不是删到最后一张。若只是**临时**把原片挪走，提示里点明"放回后重跑即可"。

### D3 输出改造（对齐 CLI emoji 契约）

段标题 `数据一致性检查：` → `数据一致性检查与清理：`（现在会删文件，名字得对得上）。

| 场景 | 输出 |
|---|---|
| 无孤儿 | `  ✅ 未发现孤儿派生文件。`（不变） |
| 清理成功 | `  ✅ 已清理 N 个孤儿派生文件（原图已删、派生图残留）：` + 逐点位一行 `    点位：51 组（102 个文件）` + 合计行 |
| 闸门一命中 | `  ⛔ 有 N 个点位的原图目录读不到，本轮未清理任何文件（无法确认哪些派生图多余）：` + 逐点位 `    点位：<原始错误>` + `确认该目录存在且可读后重跑：npm run photos` |
| 闸门二命中 | `  ⛔ 「点位」的派生图将被全部清空（原图仓已无对应原片），本轮未清理任何文件。` + `     整组下线请手动执行（两处目录一起删）：` + `       rm -rf "../data/photos/<点位>" "../photos-originals/photos/<点位>"` |
| `refs/` 有孤儿 | 维持现状：`  ❗ 发现 N 个孤儿派生文件（参考图，无对应源图）：` + 路径 + `  💡 refs/ 一层沿用"只报告"，确认后自行清理：` + `rm` |

**清理成功不打印全部文件路径**（102 行噪声），改为逐点位计数；`refs/` 层维持列全路径
（数量小、且仍需人工执行 `rm`）。

要点：桩门触发时**不 `process.exit()` 硬退**，只置 `process.exitCode = 1`，让后面几段报告
（设备类型、`refs/` 残留、混合来源）照常打印 —— 用户能看到全部信息，退出码仍是非零。

### D4 代码结构：拆成可单测的纯函数

现在 `reportInconsistencies` 把"扫描"与"打印"揉在一起、且读写真实目录常量，无法单测。
拆成三层（沿用 `isRefPlace` / `preflightRefPlace` 那套"收完整路径、临时目录里可跑"的形态）：

1. `scanOrphans(originDirPath, derivedDirPath, exts, { failLoud })` —— **纯读写、零删除**。
   返回 `{ readError: Error|null, total: number, orphans: {file, fullPath}[] }`。
   - `failLoud: true`（顶层用）：原图目录 `readdir` 抛错 ⇒ `readError` 非空、`orphans: []`；
   - `failLoud: false`（`refs/` 用）：抛错 ⇒ 当作空清单（现状语义）；
   - data 侧目录不存在（点位只在原图仓）⇒ 无派生可清，正常返回空。
2. `decideCleanup(scans)` —— **纯函数**，输入各点位的扫描结果，输出
   `{ halt: null | {kind:'read'|'empty', points:[…]}, deletions: […] }`。
   优先级：闸门一 > 闸门二 > 正常删。
3. `reportAndCleanup(dirNames)` —— 编排：并发扫描顶层 → `decideCleanup` → 命中闸门则打印 + 置
   退出码；否则 `fs.unlink` 逐个删除（删除失败即抛出、走 catch 报错）+ 打合计；随后跑
   `refs/` 只报告扫描并打印。取代原 `reportInconsistencies`。

`module.exports` 追加 `scanOrphans` / `decideCleanup`（供 `test/orphan-prune.test.js`）。

## 出界清单（本次明确不做）

- **不新增** npm 脚本 / `--prune` / `--no-prune` 开关：清理只有一条路径（`npm run photos`），
  要停手只有自动闸门，不给人肉开关。日常若确实要"只产图不清理"，说明闸门没覆盖到某个
  真实场景 —— 那时再讨论，不预先埋开关
- **不清理 `refs/` 一层**（维持只报告，理由见 D1）
- **不对 RAW / 子目录做任何处理**（用户判定 over engineering，2026-10-08 撤回）
- **不做"部分点位照删"的分支**：闸门命中即本轮零删除，不做"跳过坏点位、其余照清"
- **不自动删除点位目录**（闸门二只提示手动 `rm -rf`，与 `del-photo` 的「删后为空」纪律一致）
- **不碰 `../data` 的 git 状态**（沿用 2026-09-30 决定，一致性段零 git 依赖）
- **不引入任何外部命令**（只用 Node 内置 `fs` / `path`；删除用 `fs.unlink`）
- **不改** `output.json` 的产出逻辑（清理与产出正交，仍在写盘之后进行）
- **不动**历史 plan 的既有论述（只对 `2026-09-30-photo-deletion-workflow.md` 追加「受控修订」节）

## 验收标准

隔离部分（标准 1–7）在 `/tmp` 隔离副本上跑（复制真实目录结构，**不碰真实两仓**）；
实跑部分（标准 8）由用户确认后执行（破坏性：删除真实文件）。

1. **正常清理**：临时结构"原片 2 张 + 派生 3 组（其中 1 组无对应原片）" ⇒ 跑 `photos`
   ⇒ 只删那 1 组的 2 个文件，其余 4 个文件与 `index.json` **零改动**
2. **闸门一（读失败零删除）**：把某点位原图目录设为不可读（或指向不存在路径）⇒ 本轮
   **一个文件都不删**、输出 `⛔` 段含该点位与原始错误、退出码 `1`
3. **闸门二（会删空零删除）**：某点位原片目录存在但为空、data 侧有派生图 ⇒ 不删任何文件、
   输出 `⛔` 段含可复制的两处 `rm -rf`、退出码 `1`
4. **优先级**：同时存在"读失败点位"与"会删空点位" ⇒ 走闸门一，输出只提闸门一（`decideCleanup`
   单测锁死优先级）
5. **后缀白名单**：`x_foo.webp` / `x_thumb.png` 之类**不是**派生后缀的文件不计入 `total`、
   也永不删除（单测：构造后断言 `scanOrphans.total` 不含它们）
6. **`refs/` 仍只报告**：`refs/` 下构造孤儿 ⇒ 只打印 `❗` + `rm` 文本，**文件仍在**
7. **零写回归**：无孤儿时跑 `photos` ⇒ 与改动前一样**零删除**、`output.json` 逐字节不变、
   输出含 `✅ 未发现孤儿派生文件。`、退出码不受影响
8. **真实实跑（用户确认后）**：对真实两仓跑一次 `npm run photos` —— `南京长江大桥玻璃栈桥`
   的孤儿派生图被清理（**数量以当次实测为准**，2026-10-07 是 102 个 / 7.34 MB / 51 组），
   其余点位零改动；`git -C ../data status` 只出现该点位下被删的派生图
9. **两条命令的语义边界**：`del-photo` 仍双仓双删（不受影响）；手动删原图后跑 `photos`
   自动收尾（本次新增能力）
10. **门禁**：`npm run test:cli` 全绿（新增 `test/orphan-prune.test.js`）；
    eslint（`src` / `test` / `new-place.js` 等，`--max-warnings=0`）零 warning

## 风险

- **唯一实质取舍**：`npm run photos` 从一个"只产出"的脚本变成"产出 + 删文件"的脚本。
  缓解 = 两道闸门（读失败 / 会删空即零删除）+ 只删三种派生后缀 + 不碰 `index.json` / 目录。
  可逆性：删除的是**可再生**的派生图（原片还在就能重跑重建）；真正不可逆的只有
  "原片已删、且派生图从未提交 git"的组合 —— 而那恰恰是本次要清理的对象，且闸门二会在
  整点位归零时停下问你。
- **闸门一可能被"无害的读失败"误触**：例如参考态点位若其原图仓目录被手删（罕见），
  顶层读失败会让整轮零删除。属 fail-safe（不删任何东西 + 提示点位名），可接受；不为此
  加例外分支。
