## 背景（自包含，零上下文可读）

站点是照片地图。**真相源**（原图，不可再生）在 `../photos-originals/photos/<点位>/`；
**派生图**（可再生）与 `index.json` 在 `../data/photos/<点位>/`。`process-photos.js`
（`npm run photos`）扫描两侧并集的全部点位 → 逐点位预检（只读、零写操作，"能不能产出"的唯一
判定点）→ 生成阶段为每张媒体产出 2 个派生文件：

| 媒体 | 派生文件 |
|---|---|
| 照片（jpg / jpeg / heic / tiff） | `<名>_thumb.webp`（300px）+ `<名>_display.avif`（1920px q50） |
| 视频（mp4） | `<名>_thumb.webp`（封面帧）+ `<名>_web.mp4`（转码版） |

## 根因：不是"文件夹多"，而是每张照片都在重新编码

### 实测：单张耗时拆解（本机，2026-10-05）

| 步骤 | 耗时 | 占比 |
|---|---|---|
| sips 把 HEIC 转 JPEG | 96–128 ms | ~12% |
| 缩略图 `_thumb.webp` | 33–44 ms | **~4%** |
| **展示图 `_display.avif`（1920px q50）** | **727–1003 ms** | **~84%** |

即单张 ≈ 0.9–1.1 s，展示图 AVIF 编码吃掉八成。全量 163 个媒体 = 326 个派生文件，
每次运行**全部重新编码**（实测全量 2 分 24 秒，与 `docs/data-pipeline.md:128` 记录吻合；
`Promise.all` 全并发拿不到并行收益——libvips 内部本就在抢核）。

### 关键：照片的生成阶段没有任何跳过判据

`buildGroup()`（约 839–980 行）照片分支**无条件**调用 `generateThumbnail` +
`generateDisplayImage`。视频分支的 `generateWebVideo`（约 293 行）第一行就是
`if (await derivedIsUpToDate(sourcePath, outputPath)) return;`——**这个判据已存在，只是
没用到照片上**（`generateVideoThumbnail` 同样没有）。

### 实测：当前状态下，324 / 326 个派生文件都是"已是最新"

对真实两仓跑判据（只读）：

```
总媒体: 163 | 照片 160 | 视频 3
派生文件总数: 326 | 跳过 324 | 需重建 0 | 缺失 2
缺失明细:
  N 北京市-大兴机场/IMG_4666_thumb.webp
  N 北京市-大兴机场/IMG_4666_display.avif
预检耗时（全并发读 EXIF，含视频 exiftool）: 256 ms
```

- 那 2 个缺失正是用户刚加进 `北京市-大兴机场` 的 `IMG_4666.HEIC`（`output.json` 里该点位
  仍是 `photos: 1`，只有 `IMG_4657`）
- data 仓现有展示图**全部已是 AVIF**（`_display.webp` 残留 0 个）→ 落地后不存在新旧档位混合

**结论**：加上增量跳过后，同样一条 `npm run photos` 全量命令 ≈ 0.26 s（预检）+
0.8 s（只编码那 1 张）= **约 1.1 秒**。不需要新参数，不需要改 `output.json` 语义。

## 方案

### 1. 判据统一（唯一的改动实质）

复用**已有的** `derivedIsUpToDate(sourcePath, derivedPath)`（约 269 行）：

```
派生文件存在 且 派生 mtime ≥ 原片 mtime  →  跳过编码
```

判据必须用同一个函数、同一个比较符（`>=`），**不新增第二套口径**。落到 4 个生成函数：

| 函数 | 现状 | 改动 |
|---|---|---|
| `generateWebVideo` | 已有判据 | 不动（只加计数） |
| `generateThumbnail` | 无 | 入口加判据，命中即 `return` |
| `generateDisplayImage` | 无 | 入口加判据，命中即 `return` |
| `generateVideoThumbnail` | 无 | 入口加判据，命中即 `return` |

照片的两个派生文件**各自独立判定**（thumb 存在但 display 缺失的混合态能各自补上）。

**失败方向是安全的**：原片 mtime 变新（fix-gps 补坐标、重新拷贝覆盖）→ 派生图判为过期 →
重建。宁可多算，不会漏算。

### 2. 收尾汇总一行（可见性）

跳过时逐张不打印（避免刷屏），生成阶段结束后打印一行文件级计数，风格对齐既有的
"数据一致性检查""设备类型识别"两个收尾报告：

```
派生图增量：
  ℹ️ 复用 324 个（原图未变动）、重新生成 2 个
```

用 `ℹ️`（提示，素文本）而非 `⏭️`——`⏭️` 在本 repo 的契约里是"有问题或本轮未产出、须注意"
（黄色，现用于"未通过预检的文件夹"）；增量复用是正常行为，不该带上警示色。

### 3. `--force` 开关（**已拍板：加**，用户 2026-10-05）

`photos` 目前**没有任何参数解析**。加一个最小 `parseArgs`（风格对齐 `fix-gps.js` /
`new-place.js`：未知参数抛 `Error` → 打印用法 → `exit 1`）：

```
npm run photos               # 增量（默认）
npm run photos -- --force    # 忽略判据，全部重新生成
```

**为什么需要**：mtime 判据有三类已知失灵场景（见下），`--force` 给它们一个**统一且显式**的
出口，而不必为每种情况设计自动探测（自动探测 = 第二套判据，与"判定点单一"的偏好冲突）。

`--force` 的语义边界：**只影响"是否重算"，不影响任何判定与产出内容**——预检判据、跳过清单、
退出码、`output.json` 内容三者都不因它改变（验收 6 锁定这一点）。

**已知失灵场景（本计划不自动处理，只记录）**：

1. **改档位常量后**（`DISPLAY_QUALITY` / `DISPLAY_SIZE` / `THUMB_SIZE` / `THUMB_QUALITY` /
   `VIDEO_CRF`）：旧派生图 mtime 仍 ≥ 原片 → 被跳过，**静默沿用旧档位**。视频今天已有同一
   性质（改 CRF 后旧 `_web.mp4` 不会被重转），本次只是把该性质扩展到照片
2. **派生文件损坏 / 0 字节**（上次运行中途被 Ctrl+C）：文件存在即被跳过，破图留存
3. **原位覆盖同名原片**且新文件 mtime 更早（如 `rsync -a` 从备份恢复，保留了旧 mtime）

（plan 阶段曾权衡"不加 `--force`、改档位时手动删派生图"这一备选，但删除属破坏性操作
（P2 需当次确认），且 `photo-ops.md:26` 已记录为这类事情付手工成本不合算——
**用户 2026-10-05 明确要求加**。）

## 被否决的方案（P1：保留决策过程）

| 方案 | 做法 | 否决理由 |
|---|---|---|
| **`--dir` 限定点位**（用户本轮已明确不选） | `npm run photos -- "北京市-大兴机场"` | ① 必须新增 `output.json` "读旧 → 替换该条 → 其余保留"的局部合并语义，否则其余 14 个点位会从地图上消失（现行为是整文件重写）；② **解决不了主要痛点**——往 44 张的点位里加 3 张仍要全量重编该点位（~42 s），而增量跳过把它降到 ~3 s |
| **按内容哈希判定** | 派生文件旁存原片哈希，不符才重建 | 第二套判据 + 需要额外存储；mtime 判据在用户真实路径（新增/覆盖照片）下已足够 |
| **派生文件名带档位指纹** | 如 `<名>_display.q50.avif` | 破坏 `displayLink` 的 URL 契约，前端与已发布的 data 仓地址全部失效 |
| **档位指纹文件**（比对不一致即报错退出） | data 仓写 `pipeline-fingerprint.json` | 给 data 仓引入新的状态文件与同步义务，成本 > 收益（改档位是低频动作，`--force` 已覆盖） |
| **比对文件大小 / 格式** | 顺带校验派生文件非空、格式匹配 | 第二套判据；`--force` 已是统一出口 |

## 出界清单（本计划明确不做）

- **不改** `output.json` 的产出语义（仍全量重算、整体覆盖；不加 `--dir`、不加局部合并）
- **不改**任何预检判据与失败粒度（缺 GPS / 缺 `index.json` 的口径一字不动）
- **不改** `del-photo.js`：它的"不自动重跑管线"（`photo-ops.md:26`，2026-09-30 v4）**前提
  就是"重跑很贵"**——本计划落地后该前提失效（重跑降到 ~1 秒），但**翻案权在用户**，
  agent 不擅自改另一条决策；只在 `photo-ops.md` 加一句标注前提已变
- **不删除 / 不清理**任何既有派生文件（P2：破坏性操作需当次确认）
- **不动** `AGENTS.md` 路由表（知识进既有域文件，按流程 #3）
- **不改** `fix-gps.js` / `delete-photo.js` / `new-place.js`
- **不做**并发度调优（既然绝大多数会被跳过，控制并发已无意义）

## 验收标准

1. **增量命中（主指标）**：真实两仓下跑 `npm run photos` → 输出"复用 324 个、重新生成 2 个"，
   总耗时 **< 3 秒**（对照：改动前同条件 1 分钟以上）
2. **零副作用**：上述一次运行后，除 `北京市-大兴机场/IMG_4666_{thumb.webp,display.avif}`
   与 `src/Application/output.json` 外，data 仓**任何文件 mtime 不变**（mtime 指纹前后对比）
3. **产出等价**：同一输入下，增量跑出的 `output.json` 与 `--force` 全量重建跑出的
   **逐字节一致**（md5 比对）
4. **新增即生成**：往某点位复制一张新照片 → 跑 → 只多出该张的 2 个派生文件，其余不变
5. **原片更新即重建**：`touch` 一张原片 → 跑 → 该张的 2 个派生文件 mtime 均更新
6. **`--force` 全量重建**：所有 326 个派生文件 mtime 全部更新；且 `--force` 只影响"是否重算"，
   不改变产出内容与判定结果（退出码、跳过清单与增量跑一致）
7. **未知参数硬拦**：`npm run photos -- --foobar` → 打印 `❌ 未知参数：--foobar` + 用法 +
   `exit 1`，**零副作用**（对齐 `new-place.js` 的既有行为）；不带参数时正常增量运行
8. **汇总行可读**：含复用数与生成数；非 TTY / `NO_COLOR` 下无 ANSI 转义码
9. **门禁**：eslint（`src` / `test` / `*.js`，`--max-warnings=0`）零 warning；
   `npm run test:cli` 全绿（含新增用例）
10. **S1 数据隔离**：验收 1–8 在 `/tmp` 隔离副本上跑（复制真实照片，不碰真实两仓）；
    最终在真实两仓只跑一次验收 1（只读原图，写派生图是既有行为）

## 风险

- **`--force` 已定：加**（用户 2026-10-05 拍板，见方案 3）。成本 = 一个参数 + 约 20 行参数解析；
  收益 = 给 mtime 判据的三类失灵场景一个显式复位入口。此项落定后，本计划**无待定项**。
- **mtime 判据的固有局限**（3 类，见方案 3）不解决，靠 `--force` 出口。判定失败方向安全
  （原片更新 → 重建，不会漏算）。
- 破坏性风险：**零**。本计划不删除任何文件；唯一行为变化是"少写一批本来就会重写的派生文件"。
- 落地时机有利：data 仓现有展示图**已全部是 AVIF q50**（`_display.webp` 残留 0），落地即
  全量命中增量，不会出现新旧档位混合。
